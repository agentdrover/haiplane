# Локальный ревьюер: включение и изоляция (#1180)

Хаб умеет добывать машинное ревью двумя способами. Облачный (Cursor Cloud
Agents) работает только с GitHub — измерено 31.08.2026: одинаковое тело
запроса, адрес `gitverse.ru` даёт 400, `git@gitverse.ru` — 500, контрольный
`github.com` — 201, а в доке Cursor поле прямо названо «GitHub repository
URL» (#1119). Локальный запускает агентский CLI на хосте хаба и работает на
любом форже.

Пока локальный путь не включён, на не-GitHub проектах независимого машинного
ревью НЕТ ВООБЩЕ: отчёт может подать только тот, кто делал работу, и при
`REVIEW_SELF_APPROVE=forbid` гейт его не засчитывает. Наблюдено на живой
задаче #1128 (05.09.2026, snip-portal): настоящий прогон харнесса нашёл семь
вещей, отчёт был сдан принципалом автора, задача простояла девять часов без
вердикта. Поэтому **автопилот вердикта на таких проектах включать нельзя,
пока здесь не появится ревьюер**.

## Решение об изоляции и почему именно оно

Разобрано по видам вреда, а не по общему ощущению «пусть будет контейнер».
Ревьюер — это агентский CLI общего назначения: он умеет запускать команды и
писать файлы. Промт харнесса запрещает ему лазить по репозиторию, но это
**просьба, а не песочница**.

| Вред | Чем закрывается |
|---|---|
| Чтение секретов (`secrets.env`, ключ Cursor, deploy key, админские токены) | Отдельный unix-пользователь: `secrets.env` лежит `0600 root:haiplane`, чужой пользователь его не прочтёт. Плюс окружение процесса собирается белым списком, а не копией окружения хаба |
| Порча рабочего клона, которому доверяет гейт доставки | Клон ревьюеру **не даётся вовсе**: дифф уезжает ему инлайном в промте, а предмет ревью он читает по HTTP через `review-brief`, который берёт данные из клона хаба и к форжу не ходит (проверено вызовом на GitVerse-задаче #1138) |
| Съедание CPU и памяти (харнесс — это 4–25 агентов) | Лимиты на запуске: `--property=MemoryMax`/`CPUQuota` у systemd-run либо `--memory`/`--cpus`/`--pids-limit` у podman. У rootless podman они держатся только после делегирования cgroup-контроллеров (шаг 4) — без него лимит молча не применяется вовсе |
| Затаскивание зависимостей (node и окружение CLI) на хост, который намеренно держится без node и npm | **Только здесь контейнер даёт настоящую выгоду.** Если выбранный CLI тянет node — берите контейнер как обёртку запуска (`HAIPLANE_LOCAL_REVIEW_SANDBOX`), но ради изоляции зависимостей, а не «чтобы прод не пострадал»: контейнер делит с хабом ядро, диск и процессор |

Итого: **отдельный пользователь + лимиты + отсутствие клона** — базовая
конфигурация, и она нужна в любом случае. Контейнер — необязательная надстройка
под конкретный CLI. Если цель формулируется как «прод точно не пострадает»,
честный ответ — отдельный хост, а не контейнер.

Песочница обязательна: пустая `HAIPLANE_LOCAL_REVIEW_SANDBOX` означает
«локального пути нет», а не «запускай как есть».

## Требование к обёртке: потомок ИЛИ собственный срок жизни

Хаб снимает зависший прогон, убивая группу СВОЕГО процесса. Поэтому обёртка
обязана дать ему одно из двух:

* либо оставить CLI **прямым потомком хаба** — тогда убийство группы доходит
  до полезной нагрузки;
* либо иметь **собственный срок жизни** — тогда прогон умрёт сам, даже если
  убийство до него не дошло.

Первая редакция этого документа требовала только потомка. Выкат 08.09.2026
показал, что для контейнеров это требование недостижимо в принципе: `podman
run` переживает убийство группы — `kill -KILL` по группе, через 7 секунд
контейнер `Up`, потому что `conmon` намеренно отсоединён от клиента podman.
С `podman run --timeout 5` тот же опыт даёт другой исход: через 12 секунд
живых контейнеров нет. (Измерено на agenthai: Ubuntu 22.04, podman 3.4.4,
systemd 249.)

Чем плохо отсоединение само по себе — двумя разными отказами, найденными ревью
на первой редакции:

* `systemd-run` без `--scope` поднимает transient **service** — родителем CLI
  становится PID 1. Хаб убивает группу СВОЕГО процесса, то есть клиента
  systemd-run, юнит при этом продолжает работать, а в ленте задачи стоит
  «процесс и вся его группа убиты». Управление, которое отчитывается об
  убийстве, ничего не убив, — хуже отсутствующего;
* тот же сервисный режим не передаёт полезной нагрузке ни `cwd`, ни окружение:
  каталог-однодневка и белый список переменных оседают на клиенте. Ревьюер
  пошёл бы работать в свой unix-home, а не в одноразовый каталог.

`--scope` закрывает оба: процесс остаётся ребёнком хаба, наследует cwd,
окружение и stdin, а лимиты (`--property=MemoryMax`, `CPUQuota`) на scope
работают так же, как на service. `--pipe` при этом не нужен и не указывается:
stdin наследуется напрямую.

Хаб проверяет эти случаи и ОТКАЗЫВАЕТСЯ запускать прогон, называя в карточке
**недостающий флаг**, а не «песочница неверна»:

| Что написано в песочнице | Что скажет хаб |
|---|---|
| `systemd-run` без `--scope` | добавьте `--scope` |
| `podman run` без `--timeout` | добавьте `--timeout <секунды>` |
| `podman run --timeout 0` (и любое нечисловое значение) | срок — целое число секунд БОЛЬШЕ НУЛЯ; ноль это подман-умолчание |
| `docker run` | флага собственного срока жизни у docker нет вовсе — возьмите `podman run --timeout` либо обёртку, оставляющую CLI потомком |
| `podman run --timeout 1800 --timeout 0` | судится ПОСЛЕДНЕЕ вхождение: здесь действует ноль, и хаб откажет по нему |

**Проверка знает названные инструменты и названные флаги — и только их.**
Это факты про systemd-run, podman и docker, а не догадка про песочницы вообще.
Всё, чего проверка не знает, она ПРОПУСКАЕТ. В частности, обёртка-скрипт,
внутри которой лежит `podman`, для хаба непрозрачна: он видит только `sudo` и
путь к скрипту. Срок жизни внутри такой обёртки — на вашей совести, и рецепт
ниже прописывает `--timeout` в самом скрипте именно поэтому.

`--timeout 0` сроком жизни НЕ является, и хаб его отвергает: ноль — это
подман-умолчание, а умолчание задокументировано словами «By default
containers run until they exit or are stopped by `podman stop`»
(podman-run(1)). Тот же отказ идёт на значение, которого нет вовсе
(`--timeout` последним токеном) и на нечисловое. Это тот же класс, что
`--timeout` после образа: токен в строке есть, а снять прогон нельзя
(найдено машинным ревью 09.09.2026, находка fee582c0e918a6a6).

**Повторённый флаг судится по ПОСЛЕДНЕМУ вхождению — как его читают сами
инструменты.** В `podman run --timeout 1800 --timeout 0` действует ноль, и
хаб откажет; в `--timeout 0 --timeout 1800` действует 1800, и он запустит.
То же правило и для пользователя песочницы: в `sudo -u alice -u bob` запуск
идёт под `bob`, и членство в группе каталога прогонов хаб проверяет у `bob`.
Замерено 10.09.2026 на обоих разборщиках (живого podman и systemd-run под
рукой не было — замерены их разборщики): `spf13/pflag`, которым разбирают
командную строку podman и docker, — `docker context ls --format '{{.Name}}'
--format 'LAST_WINS'` печатает `LAST_WINS`, обратный порядок печатает имена
контекстов; `getopt_long`, которым разбирают её sudo(8) (`parse_args.c`) и
systemd-run, — на `-n -u alice -u bob` даёт `bob`. Раньше хаб судил по
первому вхождению, то есть не видел ничего, дописанного правее (найдено
машинным ревью 09.09.2026, находка 04d3d4b0f7febee0, и работой над #1208).

`--timeout` засчитывается только среди флагов САМОГО `run` — до имени образа.
Всё, что стоит после образа, — команда внутри контейнера, и её `--timeout`
сроком жизни контейнера не является: `podman run --rm -i img agent --timeout
60` отсоединяется ровно так же и отвергается (найдено машинным ревью
09.09.2026, находка 2e24a6068bbc3fa1). Глобальные флаги движка со значением
отдельным токеном (`podman --log-level debug run …`) хаб знает по имени и
пропускает вместе со значением; **глобальный флаг, которого он не знает по
имени, съест подкоманду, и запуск контейнера останется невидимым** — если
пишете такой, пользуйтесь формой `--flag=value`: она от списка имён не
зависит вовсе.

То же и с пользователем песочницы: хаб вычитывает его из `--uid` (systemd-run)
и из `-u` / `--user` (sudo), включая слипшуюся запись `sudo -nu <имя>` и
`-u<имя>`, чтобы проверить его членство в группе каталога
прогонов. `--user` за `podman` или `docker` он к хосту НЕ относит — это
пользователь внутри контейнера. Если ваша обёртка называет пользователя
как-то иначе, проверка группы просто не сработает, и корректность каталога
останется на вас.

## Настройка

Все имена настроек несут префикс `HAIPLANE_` — его подставляет `config.env_get`
в `hub/config.py`. **Без префикса переменная не читается вовсе**, а локальный
путь при этом не ломается, а молча выключается: в карточке встанет «локальный
не настроен» при полностью верной во всём остальном конфигурации. Первая
редакция этого документа писала их без префикса, и выкат 08.09.2026 потратил на
это отдельный заход. Теперь совпадение имён документа с тем, что читает код,
проверяется тестом
(`tests/test_review_dispatch.py::test_the_deploy_doc_names_the_settings_the_code_reads`),
а не внимательным чтением.

Четыре обязательные переменные (drop-in `systemd`, `chmod 600`):

```ini
[Service]
Environment=HAIPLANE_LOCAL_REVIEW_CMD=<argv агентского CLI>
Environment=HAIPLANE_LOCAL_REVIEW_SANDBOX=/usr/bin/sudo -n -u haiplane-reviewer /usr/local/bin/haiplane-review-run
Environment=HAIPLANE_LOCAL_REVIEW_SCRATCH_DIR=/var/lib/haiplane-review/scratch
Environment=HAIPLANE_LOCAL_REVIEWER_HUB_TOKEN=<ключ принципала local-reviewer>
# Необязательные, здесь показаны с умолчаниями:
# HAIPLANE_LOCAL_REVIEW_TIMEOUT_SEC=1800
# HAIPLANE_LOCAL_REVIEW_TOKEN_CEILING=2000000
```

Почему именно `sudo`, а не `systemd-run --uid=`, который стоял здесь раньше:
**строка с `systemd-run --uid=` на этом проде не запускается вовсе.** Хаб
работает под непривилегированным пользователем, а смена uid у systemd-run идёт
через polkit — измерено 08.09.2026: `Failed to start transient scope unit:
Interactive authentication required`. Выкат по прежнему документу
останавливался на первом же запуске. Форма `systemd-run --scope --uid=…`
остаётся законной и хабом принимается — но только там, где у пользователя хаба
есть на неё право (root или настроенное правило polkit).

Порядок:

1. **Пользователь.** `useradd --system --home /var/lib/haiplane-review
   haiplane-reviewer`. Он НЕ входит в группу `haiplane`, под которой работает
   хаб, — иначе он получил бы доступ к тому, ради чего всё это и затевалось.
   Общая у них ровно одна группа, и только на каталог прогонов (шаг 2).
2. **Каталог прогонов.** `/var/lib/haiplane-review/scratch`, владелец
   `haiplane-reviewer`, группа `haiplane-review`, режим `2770`. В этой группе
   состоят ОБА: и пользователь хаба, и пользователь ревьюера — каталог
   прогона создаёт хаб, а работает в нём ревьюер. Setgid (первая двойка) даёт
   подкаталогам ту же группу, а хаб доставляет им режим `0770` сам: без этого
   `mkdtemp` оставил бы `0700` на своём владельце, и ревьюер получил бы отказ
   на собственный рабочий каталог. Хаб удаляет каталог после прогона.

   Каталог создаёте ВЫ, а не хаб: созданный им на лету, он получил бы основную
   группу хаба — ровно ту, куда ревьюеру хода нет. Поэтому хаб отказывается
   запускать прогон и называет причину, если каталога нет, если на нём нет
   setgid, если пользователь из песочницы не состоит в группе каталога или
   если этого пользователя (хоть по имени, хоть по числовому uid) не удалось
   разрешить в системе: «не смогли проверить» — это причина отказа, а не
   разрешение работать.
3. **Враппер и правило sudo.** Скрипт `/usr/local/bin/haiplane-review-run`
   принадлежит `root:root`, режим `0755`, и все флаги запуска зафиксированы
   ВНУТРИ него — **кроме argv самого CLI: его дописывает хаб**, и об этом
   ниже отдельно. В sudoers прописан ровно один путь, **без единой
   подстановки** — иначе `sudo` превращается в дыру шире той, которую он
   закрывает:

   ```
   # /etc/sudoers.d/haiplane-review, режим 0440, проверять visudo -cf
   haiplane ALL=(haiplane-reviewer) NOPASSWD: /usr/local/bin/haiplane-review-run
   ```

   **Что это правило закрепляет — и что нет.** Оно закрепляет КОМАНДУ, а не
   её аргументы: по sudoers(5) «if no command line arguments are specified,
   the user may run the command with any arguments they choose». Пользователю
   хаба, стало быть, разрешено дописать к врапперу любые аргументы — и он это
   делает, потому что хаб запускает `shlex.split(SANDBOX) + shlex.split(CMD)`
   (`local_reviewer.argv()`). Дописанное — это argv агентского CLI, и попадает
   оно внутрь контейнера, после образа. Хотите закрепить и аргументы — пишите
   в sudoers argv целиком, слово в слово совпадающий с
   `HAIPLANE_LOCAL_REVIEW_CMD`; форма `…haiplane-review-run ""` запретит
   аргументы вовсе — а вместе с ними и локальный путь, потому что пустой
   `HAIPLANE_LOCAL_REVIEW_CMD` его выключает.

   Промт доезжает врапперу в stdin и уходит в контейнер через `-i`; ответ
   возвращается в stdout. Скелет враппера:

   ```sh
   #!/bin/sh
   set -eu
   exec /usr/bin/podman run --rm -i \
        --timeout 1800 \
        --memory 1500m --cpus 1.5 --pids-limit 512 \
        --env-file /etc/haiplane-review/env \
        --network none \
        haiplane-review:latest "$@"
   ```

   **`"$@"` в последней строке — не украшение.** Без него враппер молча
   выбрасывает argv, который хаб к нему дописал. Измерено на скелете ИЗ ЭТОГО
   документа (09.09.2026, находка машинного ревью 8d363dc407782056): запуск
   `haiplane-review-run cursor-agent --print --model …` доходит до podman
   строкой БЕЗ `cursor-agent`, код возврата 0, ни ошибки, ни следа в ленте.
   Запустится то, что зашито в образ, а не то, что стоит в
   `HAIPLANE_LOCAL_REVIEW_CMD`, — тот же класс отказа, ради которого писан
   весь этот документ: не ломает, а тихо подменяет. Совпадение скелета с тем,
   как хаб склеивает argv, проверяется тестом
   (`tests/test_review_dispatch.py::test_the_doc_wrapper_carries_the_argv_the_hub_appends`),
   а не внимательным чтением.

   `"$@"` нужен и тогда, когда argv CLI зашит в образ через `ENTRYPOINT`:
   пустым `HAIPLANE_LOCAL_REVIEW_CMD` быть не может — пустой выключает
   локальный путь целиком, — то есть хаб всё равно что-то допишет, и это
   «что-то» обязано доехать до контейнера, а не потеряться по дороге.

   `--timeout` здесь не украшение: без него контейнер переживает снятие
   прогона (см. раздел про обёртку). Держите его не меньше
   `HAIPLANE_LOCAL_REVIEW_TIMEOUT_SEC`, иначе контейнер начнёт умирать раньше,
   чем хаб успеет счесть прогон зависшим.
4. **Делегирование cgroup — иначе лимиты молча не применяются.** Rootless
   podman без делегированных контроллеров тихо падает в cgroupfs, и `--memory`
   не действует ВООБЩЕ: измерено 08.09.2026 — `memory.max = max` при заданном
   `--memory 1500m`. Ошибки при этом нет, есть только отсутствие лимита.

   ```ini
   # /etc/systemd/system/user@.service.d/delegate.conf
   [Service]
   Delegate=cpu cpuset io memory pids
   ```

   Затем `systemctl daemon-reload` и `loginctl enable-linger haiplane-reviewer`
   — без linger пользовательская шина ревьюера не живёт между запусками, и
   делегирование не к чему применить. После этого на том же прогоне измерено:
   `memory.max = 1572864000`, `cpu.max = 150000 100000` — то есть 1500 MiB и
   1.5 ядра держатся.
5. **Принципал и токен.** Свой агентский принципал `local-reviewer` и его
   ключ — не общий с `cursor-cloud-reviewer`: независимость отчёта держится
   тем, чей токен его принёс (#728), а отзывать локального ревьюера надо уметь
   отдельно — он исполняется на хосте хаба.
6. **CLI.** Ставится ПОД ПОЛЬЗОВАТЕЛЕМ ревьюера (в образе контейнера или в его
   unix-home), а не глобально на хосте. Промт уходит ему в stdin: аргументы
   видны в `ps` любому пользователю хоста, а промт несёт одноразовый код
   доступа к хабу.
7. **Политика проекта.** `gate_policy.review = dispatch` — та же, что у
   облачного пути. Локальный путь ей подчиняется, отдельного тумблера нет.

## Проверка попыткой, а не чтением конфига (AC-2 задачи #1180)

Настройка, о которой только заявлено, защитой не является.

**Пути спрашиваются у системы, а не берутся из этого документа.** Первая
редакция называла их литералами — и оба промахнулись мимо живой установки
(найдено ревью, находки 85870ae1 и cab0aab3). Промах здесь дороже, чем
кажется: `cat` несуществующего файла тоже отказывает, и проба, которая не
отличает «нет прав» от «нет файла», доказывает пустоту, а не защиту. Плюс
каталог службы на этом проде до сих пор носит имя времён до ребрендинга,
которого в тексте репозитория быть не может, — ещё одна причина не писать
такие пути литералом.

```bash
HUB_UNIT=<имя systemd-юнита хаба>
# Ведущий '-' в EnvironmentFile — это «файла может не быть», а не часть пути.
# Снимать его надо ИМЕННО ведущий: tr -d '-' съедает и дефисы внутри пути
# (найдено ревью, находка f1fee6de — /etc/haiplane-hub стал бы /etc/haiplanehub).
SECRETS=$(systemctl show "$HUB_UNIT" -p EnvironmentFile --value \
          | tr ' ' '\n' | grep -i secrets | sed 's/^-//')
WORKSPACE=<workspace_path проекта — со страницы /projects или GET /api/projects>

# 0. Сначала убедиться, что цели СУЩЕСТВУЮТ и что это именно они: иначе
#    отказ ниже не значит ничего. Подставленный руками путь легко оказывается
#    чужим каталогом, и ENOENT от него читается как «защищено».
sudo test -f "$SECRETS"  && echo "файл секретов на месте: $SECRETS"
sudo git -C "$WORKSPACE" rev-parse --git-dir >/dev/null \
  && echo "рабочий клон на месте: $WORKSPACE"

# 1. Под пользователем ревьюера обе попытки обязаны отказать ПО ПРАВАМ.
sudo -u haiplane-reviewer cat "$SECRETS"            # ожидается Permission denied
sudo -u haiplane-reviewer touch "$WORKSPACE/PROBE"  # ожидается Permission denied

# 2. А сама песочница обязана пройти — ПОД ПОЛЬЗОВАТЕЛЕМ ХАБА, потому что
#    запускать её будет именно он. Проба из-под root ничего не доказывает:
#    прежняя редакция рекомендовала systemd-run --uid=, и она отказывает
#    непривилегированному хабу через polkit («Interactive authentication
#    required»), а из-под root проходит.
#
#    argv CLI дописывается ОБЯЗАТЕЛЬНО, тем же составом, что в
#    HAIPLANE_LOCAL_REVIEW_CMD: хаб склеивает SANDBOX и CMD, и проба без CMD
#    проверяет другую команду. Прежняя редакция гоняла враппер голым — и
#    прошла бы на скелете, который argv молча выбрасывает.
CMD=<то же значение, что в HAIPLANE_LOCAL_REVIEW_CMD>
sudo -u haiplane /usr/bin/sudo -n -u haiplane-reviewer \
     /usr/local/bin/haiplane-review-run $CMD </dev/null

# 3. Лимиты обязаны БЫТЬ, а не быть заявленными: rootless podman без
#    делегирования молча работает без них.
sudo -u haiplane-reviewer podman run --rm --memory 1500m --cpus 1.5 \
     haiplane-review:latest cat /sys/fs/cgroup/memory.max   # не должно быть 'max'
```

Если отказала вторая команда, песочница не запустится — и хаб честно напишет в
карточку, что прогона не было, а не сделает вид, что ревью прошло. Если третья
напечатала `max`, лимиты не применены: вернитесь к шагу 4 настройки
(делегирование и linger).

## Что видно в карточке задачи

* запуск: «Машинное ревью запущено ЛОКАЛЬНО: форж «…» облачному ревьюеру
  недоступен…»;
* не настроено: «Машинное ревью НЕ вызвано: … локальный не настроен: <имена
  недостающих настроек>» — имена, никогда не значения;
* потолок: «потолок стоимости исчерпан: на задачу уже потрачено N токенов при
  потолке M»;
* обёртку нельзя снять: «systemd-run без --scope запускает transient
  service…», «podman run без --timeout отсоединяет контейнер…», «docker run …
  флага собственного срока жизни у него нет вовсе» — прогон не начинается
  вовсе, и в каждом случае названо, ЧЕГО не хватает;
* зависший прогон: «снято по таймауту (N с): процесс и вся его группа убиты»;
* прогон завершился сам, но без разбираемого отчёта: «завершилось без отчёта:
  код возврата N, прогон занял M с…» с хвостом вывода;
* **штатная остановка или рестарт хаба**: «снято при остановке хаба: процесс
  убит вместе с хабом, отчёта нет». Это обычный путь — его пишет сам хаб,
  снимая свои прогоны;
* **прогон, оставшийся от ДРУГОГО процесса хаба** (упал, был убит снаружи):
  «Локальное машинное ревью потеряно…», и не сразу, а по истечении grace,
  который не короче таймаута прогона. Раньше этот текст стоял здесь как исход
  обычного рестарта — то есть документ обещал искать в карточке не ту строку
  (найдено ревью, находка 14a1a965).

Ни один из этих исходов не значит «прочитано и чисто»: вердикт в каждом
остаётся человеку.
