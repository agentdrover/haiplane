# Continuous Deployment: auto-deploy on merge to `main`

Каждый push в `main` (то есть любой merge PR в `main`) автоматически выкатывает код
на текущий production-like сервер. Деплой выполняется GitHub Actions и повторяет
ручной процесс из `docs/agent-deploy-runbook.md` раздел 4.

## Как это работает

Workflow: `.github/workflows/ci.yml`, job `deploy`.

1. Job `static` (#1920) гоняет `ruff check`, `ruff format --check`, `mypy`,
   бюджеты, `pip-audit`, `bandit` и скан секретов параллельно частям `pytest`;
   job `test` ждёт его, краснеет по его результату и остаётся единственной
   обязательной проверкой «Ruff and pytest» и сборщиком отчёта для хаба.
   Рядом, параллельно, job `compose-smoke` (#1358) поднимает образ из
   `docker-compose.yml` (`deploy/docker/compose_smoke.sh`): `/healthz` с
   демо-сидом и без него, на свежем томе. В `needs` деплоя он не стоит —
   прод живёт не в этом образе. Локально: `deploy/docker/compose_smoke.sh`.
2. Job `deploy` стартует только если:
   - `test` прошёл (`needs: test`);
   - событие — это `push` в `main` (на `pull_request` деплой не запускается).
3. Шаги деплоя:
   - кладёт приватный SSH-ключ из секрета в раннер;
   - ставит `uv` закреплённой версии (та же, что в job `test` и Dockerfile) и
     Python 3.11, проверяет `uv lock --check` и экспортирует из `uv.lock` два
     хешированных набора в дерево: `requirements.runtime.txt` (без dev) и
     `requirements.build.txt` (группа `build`: hatchling и editables) (#1620);
   - `rsync` рабочего дерева в `~/haiplane-hub-src-staging` на сервере;
   - `ssh ... 'bash -s' < deploy/remote-deploy.sh` — промоут staging в
     `/opt/haiplane-hub/src`, установка наборов по lock
     (`pip install --require-hashes --only-binary=:all: --no-deps`), затем
     приложения (`pip install --no-deps --no-build-isolation -e`),
     `systemctl restart haiplane-hub`, проверка `systemctl is-active` и
     `GET /healthz`.

`concurrency.group: deploy-production` гарантирует, что два деплоя не пойдут
параллельно. Деплой привязан к GitHub Environment `production` — на него можно
повесить required reviewers / wait timer в настройках репозитория.

Логика самого деплоя живёт в `deploy/remote-deploy.sh`, чтобы её можно было
ревьюить и менять без правки YAML.

## Обязательные GitHub secrets

Настроить в **Settings → Secrets and variables → Actions** (репозиторий или
Environment `production`):

| Secret | Назначение | Пример |
|--------|------------|--------|
| `DEPLOY_HOST` | хост/IP сервера | `203.0.113.10` (пример) |
| `DEPLOY_USER` | SSH-пользователь с passwordless sudo для шагов деплоя | `deploy` (пример) |
| `DEPLOY_SSH_KEY` | приватный SSH-ключ целиком (OpenSSH/PEM), без пароля | содержимое файла приватного ключа целиком, включая строки `BEGIN`/`END` |

Требования к ключу/доступу:

- публичная часть ключа добавлена в `~/.ssh/authorized_keys` пользователя `DEPLOY_USER`;
- `DEPLOY_USER` может без пароля выполнять `sudo rsync`, `sudo chown`,
  `sudo -u haiplane ... pip`, `sudo systemctl restart haiplane-hub`,
  `sudo journalctl -u haiplane-hub`;
- для drain локальных ревью (#1588, раздел ниже) — ещё и
  `sudo -n -u <пользователь хаба> env … bash -c "<текст скрипта>" review-drain <команда>`; без этого
  разрешения деплой идёт как раньше с исходом `drain degraded`;
- для снимка базы (#1590, раздел ниже) — ещё и `sudo -n cat /proc/<MainPID>/environ`
  и `sudo -n cat <EnvironmentFile юнита>` (путь базы), а `sudo -n -u <пользователь хаба> env … bash -c …`
  из пункта выше запускает сам снимок; без этого путь базы не установлен и деплой
  **не идёт** (`backup: failed`), см. обход ниже;
- ключ хранится только в секретах GitHub. В git его класть нельзя.

## Что НЕ коммитим

Приватные ключи, токены, реальные `.env`. Секреты живут только в GitHub Actions
secrets и в `/etc/haiplane-hub/*.env` на сервере (см. runbook).

## Ручной деплой / откат

Авто-деплой не отменяет ручной путь. Если нужно выкатить или откатить вручную,
используйте `docs/agent-deploy-runbook.md` раздел 4 (тот же `remote-deploy.sh`
можно запустить руками после `rsync` в staging). Откат — задеплоить предыдущий
коммит `main` (revert PR или checkout нужного тега и ручной деплой).

## Проверка после авто-деплоя

```bash
ssh "$DEPLOY_USER@$DEPLOY_HOST" '
  echo "service=$(systemctl is-active haiplane-hub)"
  curl -sf http://127.0.0.1:8080/healthz
'
```

## Health-гейт деплоя: опрос, а не пауза (#547)

`deploy/remote-deploy.sh` после рестарта **опрашивает** `/healthz` с бюджетом
`HEALTH_BUDGET_SECONDS` (по умолчанию 60 с, интервал 1 с), а не спит фиксированные
две секунды. Успех — по первому 200.

Причина: юнит объявлен `Type=simple`, поэтому systemd считает его активным в момент
старта процесса, а uvicorn в этот момент ещё может не принимать соединения.
Наблюдение 28.07.2026 (run 30399012885): выкат прошёл полностью, `service=active`,
`healthz=000`, джоба красная. Ложно-красный деплой опаснее шумного — он приучает
читать красное как «опять гонка», и следующий настоящий сбой будет пропущен.

Три исхода различимы в логе джобы: сервис не поднялся / поднялся, но не отвечает /
отвечает. На обеих ветках отказа печатается `journalctl -u haiplane-hub -n 40`.
Раньше лог тянулся только когда сервис лежал — то есть ровно тогда, когда причина и
так очевидна.

**Время до первого 200 печатается при успехе намеренно.** Увеличенный бюджет
маскирует деградацию старта: приложение начнёт подниматься сорок секунд вместо двух,
а гейт этого не заметит. Растущее число в логе заметно глазом, молчаливый успех — нет.

### Почему не `Type=notify`

Это убрало бы гонку в корне, а не отодвигало её бюджетом, и остаётся правильным
долгосрочным решением. Но своими силами systemd этого не сделает: `Type=notify`
требует, чтобы **само приложение** отправило `READY=1` в `$NOTIFY_SOCKET` после
того, как ASGI-сервер начал слушать. uvicorn такого из коробки не умеет — нужна
доработка точки входа `haiplane-hub` (вызов sd_notify в хуке готовности FastAPI).

Это изменение приложения, а не деплоя, поэтому в #547 не вошло. Возвращаться к
вопросу имеет смысл, если время до первого 200 начнёт расти — тогда бюджет перестанет
быть страховкой и станет маскировкой.

## Зависимости прода строго по uv.lock (#1620)

Прод ставит ровно версии из `uv.lock`, которые тестировал CI (Docker ставит их
же через `uv sync --frozen`). Раньше `pip install -e` разрешал транзитивные
версии заново, и прод расходился с lock (pyjwt 2.12.1 против 2.13.0).

- **Версия uv одна** в `ci.yml` (test и deploy) и в `Dockerfile`: 0.12.18. uv
  ≥ 0.10 вычищает из lock колёса недостижимых платформ, а 0.7 понижает
  `revision`, поэтому плавающая версия переписала бы lock; тест
  `test_the_deploy_ships_hashed_lock_exports` держит равенство. Поднимать
  версию надо везде сразу и перегенерировать lock этой же версией.
- **Наборы:** `requirements.runtime.txt` (`uv export --frozen --no-dev
  --no-emit-project`) и `requirements.build.txt` (`--only-group build`). Build —
  то, что нужно editable-установке приложения без изоляции сборки: hatchling,
  его зависимости и editables. Добавлять в группу `build` — через
  `uv add --group build`; в runtime-набор те же имена попасть не должны
  (pip отвергнет дубликат; это ловит `test_the_lock_exports_install_into_a_clean_python311`).
- **Сервер** (`deploy/remote-deploy.sh`): до любых действий проверяет оба файла
  и `uv.lock` в staging; после rsync ставит оба набора одной командой с
  `--require-hashes --only-binary=:all: --no-deps` (нет колеса под Python 3.11
  сервера или хеш не сошёлся — громкий отказ), затем приложение с `--no-deps
  --no-build-isolation`. В лог идёт строка `deps: N пакетов (runtime M, build
  K) по экспортам sha256 … из uv.lock sha256 …`.
- **Отказ — до restart**, прежний процесс продолжает работать. pip не
  транзакционен: исходники и venv могут быть изменены частично, автоматического
  отката нет; восстановление — деплой предыдущего коммита тем же путём (`scripts/manual_deploy.sh`, для коммитов до #1620 с `--build-set`)
  (docs/agent-deploy-runbook.md). Лишние пакеты в venv не удаляются; pip и
  инструменты сборки venv в наборы не входят. Отдельный venv с атомарным
  переключением — вне этой задачи.
- **Закреплённая копия** `remote-deploy.sh` на сервере обновляется владельцем до
  выката (раздел про серверные копии ниже): без этого релиз встанет на
  `release_artifacts` (#1591).

## Drain локальных ревью перед рестартом (#1588)

Перед rsync `deploy/remote-deploy.sh` вызывает `deploy/review-drain.sh`:
деплой **ждёт** идущие локальные deep-ревью (Qwen через
`haiplane-review-runner`) до **1800 с** и держит маркер, по которому хаб не
стартует новые локальные заказы. Рестарт после этого снимает уже не идущий
прогон, а тот, что не уложился в срок. Протокол (файловый замок и маркер в
каталоге очереди), граница гарантии и правила хаба — в
[LOCAL-REVIEW.md](LOCAL-REVIEW.md#выкладка-хаба-деплой-ждёт-идущие-прогоны-1588).

Порядок в `remote-deploy.sh`: запуск продления маркера → `acquire` (ожидание)
→ rsync → chown → pip (наборы lock, затем приложение) → `recheck` (остаток того же срока) → restart → health →
снятие своего маркера (на успехе, ошибке и сигнале). В логе деплоя ровно
нужные строки: `drain ok`, `drain timeout (…)` или `drain degraded (…)`;
деплой от них не падает. Срок один на все ожидания, включая получение замка;
время rsync, pip и restart в гарантию не входит. Job `deploy` в `ci.yml` имеет
`timeout-minutes: 45` и ssh keepalive (`ServerAliveInterval=30`).

**Конкретный вызов, который нужно разрешить на сервере.** Каталог очереди
(`2770`, группа `haiplane-review`, владелец — пользователь хаба)
деплой-пользователю недоступен, поэтому скрипт запускается под пользователем
хаба — тем, кто владеет `/opt/haiplane-hub/src` (его уже называет
`remote-deploy.sh`):

```bash
sudo -n -u "$SERVICE_USER" env DRAIN_OWNER=… DRAIN_DEADLINE=… \
    bash -c "$(cat "$STAGING/deploy/review-drain.sh")" review-drain acquire
```

То же для `recheck`, `renew-loop` и `release` (скрипт передаётся текстом в
`bash -c`, а stdin занят каналом живучести: fifo, EOF = деплой умер). Скрипт берётся
из staging (CI rsync кладёт его туда до запуска `remote-deploy.sh`), так что
читает его (`cat`) деплой-пользователь, а не пользователь хаба. Пользователя деплоя и
его sudo проверяет и настраивает стюард на сервере до выката; код сервер не
меняет. Нет разрешения, каталога или прав — исход `drain degraded` с причиной,
деплой идёт как раньше. Каталог очереди `remote-deploy.sh` берёт из
`HAIPLANE_LOCAL_REVIEW_SPOOL_DIR` в своём окружении, а без неё — из
`Environment` юнита `haiplane-hub` (то место, где drop-in включает транспорт
`runner`); значения по умолчанию нет, не нашёл — `drain degraded`.

**Если ключ CI ограничен forced command** (схема из
[runbook](../docs/agent-deploy-runbook.md), раздел 4): правка
`deploy/remote-deploy.sh` требует обновить закреплённую копию на сервере, иначе
деплой упадёт на проверке sha256 (команды — там же). Отдельно учтите, что
`review-drain.sh` приходит через rsync в staging и исполняется под
пользователем хаба, то есть утечка ключа CI даёт запуск произвольного кода
под этим пользователем. Если это неприемлемо — закрепите копию скрипта на
сервере и укажите её через `REVIEW_DRAIN_SCRIPT` (переменная окружения
`remote-deploy.sh`): путь к файлу, читаемому деплой-пользователем.

## Проверенный снимок базы перед рестартом (#1590)

Миграции схемы идут при старте хаба, а ночной бэкап отстаёт до суток.
Поэтому `deploy/remote-deploy.sh` после `drain acquire` и **до rsync** снимает
снимок базы (`deploy/predeploy-backup.py`, из staging, под пользователем хаба):

- путь базы — **эффективный** `HAIPLANE_HUB_DB`: из окружения работающего
  процесса хаба (`/proc/<MainPID>/environ`), без процесса — из `Environment` и
  `EnvironmentFiles` юнита. Путь не определён или не читается — `backup: failed`,
  а не «базы нет»;
- sqlite backup API, база открыта `mode=ro` (не `immutable`: иначе потеряются
  закоммиченные строки из WAL), `PRAGMA integrity_check` копии, gzip с
  проверкой распаковки;
- каталог `<каталог базы>/backups` (или `BACKUP_DIR`) — `0700`, владелец
  пользователь хаба; файлы `0600`; публикация атомарная (временное имя →
  `link`), частичные файлы удаляются при ошибке и сигнале;
- имя `predeploy-<UTC>-<sha7>.db.gz`; sha CI кладёт в файл `.deploy-sha`
  дерева (форсированная команда ключа CI не пропускает ни аргументов, ни
  переменных); вручную без sha — `manual`. Хранится последних `BACKUP_KEEP=10`
  файлов `predeploy-*`, очистка — только после успешной публикации; ночные
  файлы не трогаются. Предел времени шага — `BACKUP_TIMEOUT=300` с и он не
  входит в срок drain.

Итог — одна строка в логе: `backup: ok <файл> size=<байт> integrity=ok
seconds=<N>`, `backup: failed (<причина>)` или `backup: skipped (<причина>)`.
**При `failed` скрипт выходит с ошибкой до rsync, restart не вызывается**,
drain-маркер снимается. Обещания «старая версия остаётся как была» нет:
гарантия только в том, что restart не выполнен. Записи, сделанные хабом между
снимком и restart, в снимок не попадают.

Шаг `rollout` в `ci.yml` захватывает вывод ssh, пишет строку `backup:` в
`GITHUB_OUTPUT` даже при ненулевом коде и возвращает исходный код; шаг
«Report deploy to Hub» собирает JSON сериализатором и шлёт поле `backup` в
`POST /api/deploys`. Хаб хранит итог у записи деплоя; отчёт без поля (старый
клиент) показывается как «неизвестно» и известный итог не стирает; повтор того
же `sha`/`status` итог обновляет. **Переходное:** при отказе бэкапа отчёт
принимает ещё СТАРАЯ версия хаба; пока она без поля, итог виден только в логе.

**Явный обход** — `DEPLOY_SKIP_BACKUP=1` на УДАЛЁННОЙ стороне, ручным запуском:
`ssh <DEPLOY_USER>@<DEPLOY_HOST> 'DEPLOY_SKIP_BACKUP=1 bash -s' < deploy/remote-deploy.sh`
(строка `backup: skipped (обход DEPLOY_SKIP_BACKUP=1)`). Под форсированной
командой ключа CI обхода нет намеренно. Если базы по определённому пути нет
(первая установка) — `backup: skipped (базы нет …)`, деплой идёт.

Закреплённая копия `remote-deploy.sh` на сервере обновляется до выката
(см. runbook, раздел 4); `predeploy-backup.py` приходит rsync-ом в staging.

**Первый деплой, который принесёт эту задачу, сам не защищён:** drain пойдёт
под старым хабом, не знающим маркера. Стюард следит, чтобы в этот момент не
шёл локальный deep.

## Rollout note: Universal Review Gate (2026-07)

С релиза эпика #300 (задачи #305–#311) хаб **сервером** требует ревью перед
завершением: `hub_report_done` остаётся совместимой точкой входа, но в
pair/client-флоу его результат изменился — без APPROVED-вердикта для текущего
сабмишена задача уходит в `review` (client-driven) или `ci_check`, а не в
`completed`. Клиенты, ожидавшие немедленного `completed`, должны читать
envelope ответа:

```json
{
  "status": "review",
  "awaiting": "review",
  "actor_hint": "agent",
  "next_action": "Obtain a review verdict: reviewer runs hub_get_review_brief and hub_submit_review; after APPROVED, report done again."
}
```

Откат этого поведения — только откатом релиза (см. выше): конфиг-флага нет,
гейт — инвариант жизненного цикла. Явный опт-аут на уровне задачи —
`auto_review=false`; human overrides (`hub_decide_task` accept,
`hub_force_complete_task`) работают и аудируются.

## Серверные копии артефактов сверяются до слияния релиза (#1591)

Обёртка CI запускает только закреплённую копию `deploy/remote-deploy.sh`, а
служба ревьюера ставится руками (`deploy/LOCAL-REVIEW.md`). Забытая копия
раньше проявлялась красным деплоем после слияния. Теперь авторелиз проверяет
её до слияния.

Ключ политики проекта `gate_policy.release_artifacts` — список пар
`{repo_path, server_path, update_hint}`. Только точные копии: файлы-шаблоны
(unit, env, drop-in, sudoers, обёртка `deploy/review-runner/haiplane-review-run`) законно отличаются от репо и сюда не входят. `snapshot_unpack.py` — именно точная копия: это защищённый код проверки чужого tar (#1599).
Пример для прода:

```json
{"gate_policy": {"release_artifacts": [
  {"repo_path": "deploy/remote-deploy.sh",
   "server_path": "/usr/local/sbin/<SERVICE>-remote-deploy.sh",
   "update_hint": "ssh <DEPLOY_USER>@<DEPLOY_HOST> 'sudo tee /usr/local/sbin/<SERVICE>-remote-deploy.sh >/dev/null' < deploy/remote-deploy.sh && ssh <DEPLOY_USER>@<DEPLOY_HOST> 'sudo chmod 0755 /usr/local/sbin/<SERVICE>-remote-deploy.sh'"},
  {"repo_path": "deploy/review-runner/haiplane-review-runner.py",
   "server_path": "/usr/local/lib/haiplane-review-runner/haiplane-review-runner.py",
   "update_hint": "установить файл по deploy/LOCAL-REVIEW.md и ПЕРЕЗАПУСТИТЬ службу: sudo systemctl restart haiplane-review-runner"},
  {"repo_path": "deploy/review-runner/snapshot_unpack.py",
   "server_path": "/usr/local/lib/haiplane-review-runner/snapshot_unpack.py",
   "update_hint": "установить root-овым файлом (0644 root:root) в тот же каталог, что и служба, по deploy/LOCAL-REVIEW.md «Выкат снимка»; проверка: python3 -I /usr/local/lib/haiplane-review-runner/haiplane-review-runner.py --check-install"}
]}}
```

Удаление ключа — `{"gate_policy":{"release_artifacts":null}}`. Без ключа и с
пустым списком релиз идёт как раньше.

Как это работает:

- Перед слиянием хаб берёт закреплённую голову релизного PR, считает sha256
  файла `repo_path` на этой голове (по сырым байтам blob, не по рабочей копии
  клона) и sha256 файла `server_path`. Хаб читает только хэш и содержимое никуда
  не пишет.
- Читать можно только файлы внутри каталогов из серверной настройки
  `HAIPLANE_RELEASE_ARTIFACT_DIRS` (через запятую; по умолчанию
  `/usr/local/sbin,/usr/local/lib,/usr/local/bin`). Путь абсолютный, без `..`,
  внутри каталога по границам компонентов; symlink в пути и в самом файле,
  не обычный файл — отказ. Проверка повторяется при каждом чтении, поэтому
  сохранённая политика не обходит смену списка.
- Расхождение, отсутствие или нечитаемость файла: релиз не сливается, причина
  начинается словами «серверная копия <путь> ...» и несёт короткие sha и
  `update_hint`. Это алерт `release_blocked` сразу, один до смены состояния
  (виден в карточке «Что в проде» и в ленте). После обновления копии следующий
  проход сливает сам, и алерт снимается.
- Слияние условное: GitHub получает `--match-head-commit` с проверенной головой.
  Новый push в develop между проверкой и слиянием не сливается непроверенным:
  проверка повторится на следующем проходе.

Что проверка НЕ доказывает: совпал файл на диске в момент чтения, а не версия
работающего процесса. Служба, файл которой заменён без перезапуска, продолжает
исполнять старый код, поэтому `update_hint` службы включает перезапуск. Обёртка
CI остаётся финальной защитой: проверка её не заменяет и «0 отказов деплоя» не
гарантирует.

## Возврат main в develop после релиза — PR-ом, без обхода правил (#1426)

Релиз develop → main вливается squash-ом, и после него в main лежит коммит,
которого нет в истории develop. Хаб возвращает его сам (#969). До #1426 он
делал это прямым мержем веток (`POST repos/{repo}/merges`), без PR. Правило
`pull_request` ruleset 21764773 «green CI before merge» пропускало такой мерж
только потому, что у роли **Write** в bypass стоял режим *Always allow*. Этот
же обход был открыт любому писателю: с ним можно было пушить в main и develop
мимо PR и CI. Так было до 07.10.2026: роль Write убрали из bypass без замены
(#1426) — обхода у этого ruleset не осталось вовсе, ни для кого. Отдельно и
позже, 16.10.2026, добавился новый ruleset «only the gate updates integration
branches», где обход — только учётка `haiplane-gate` (подробности —
`docs/agent-context/invariants.md`, «Личность вливания», #1708).

Теперь возврат идёт как обычная доставка:

1. Сразу после мержа релиза хаб открывает PR `main → develop`
   («chore: return main into develop after the release»). PR ищется по паре
   база `develop` + голова `main` и принимается только из этого же
   репозитория. PR из форка (`чужой:main`) и PR `main` в другую базу хаб не
   трогает. Если такие PR есть, это называется причиной в строке релиза.
2. На следующем цикле поллера хаб вливает этот PR, если CI зелёный и PR
   сливается. Вливает **мерж-коммитом** (`--merge`), а не squash, и не удаляет
   голову: голова PR — это main. Мерж записывается в `pipeline_merges` с
   номером PR возврата и без задачи, поэтому drift-guard считает его своим.
3. Красный CI, конфликт или отказ форжа на PR возврата релиз не
   останавливают. Причина называется в строке релиза. Если она держится
   несколько циклов, в ленту пишется «релиз стоит — возврат main в develop
   (PR #N) не влит: …». Чинится как обычный PR: правкой в ветке или вручную.

После этого обход требований PR/CI не нужен никому: «green CI before merge»
с 07.10.2026 не имеет обхода вовсе (роль Write убрали из bypass, #1426).
Отдельно, 16.10.2026, добавился ruleset «only the gate updates integration
branches» с обходом учётки `haiplane-gate` — это обход личности
(кто вливает в main/develop), а не обход требований PR/CI.

### Что сделать владельцу — строго в этом порядке

1. **Выкатить код** с #1426 (мерж в main, авто-деплой).
2. **Дождаться одного успешного возврата новым путём.** После следующего
   релиза в репозитории появится PR `main → develop`, и хаб вольёт его сам.
   Признак — запись в ленте «`<slug>`: main возвращён в develop (PR #N)» и
   мерж-коммит этого PR в develop. Пока такой записи нет, ruleset не трогать.
3. **Только после этого снять обход.** Settings → Rules → Rulesets →
   «green CI before merge» (id 21764773) → Bypass list → удалить роль
   **Write** (*Always allow*). Правила `pull_request`,
   `required_status_checks`, deletion и non_fast_forward не менять.

Если снять обход до выката, старый прямой мерж будет отклонён, и develop
начнёт отставать от main на один коммит за релиз — ровно то, что закрывал
#969. Шаг 2 доказывает, что новый путь работает, до того как исчезнет
страховка.

### Проверка после снятия обхода (AC-2 #1426, вручную)

- Следующий релиз: хаб открыл и влил PR возврата, в ленте есть «main
  возвращён в develop (PR #N)».
- Прямой пуш в develop пользователем с ролью Write отклонён правилом
  (`git push origin HEAD:develop` → отказ ruleset).
- Наблюдение записать в карточку #1426.

Гейт доставки вызывает `gh pr merge --admin`. Без права обхода `--admin`
ничего не обходит. Мерж проходит, когда требования ruleset выполнены (ноль
одобрений и зелёный «Ruff and pytest»), а гейт и так мержит только на зелёном
CI.

## Отчёт CI не исполняется кодом ветки задачи (#1686)

Job `test` в `ci.yml` исполняет код ветки: тесты, `conftest.py`, action и
скрипты. Поэтому в нём нет ключа, которым хаб принимает отчёт CI. Устройство:

| Шаг | Где работает | Что держит |
|---|---|---|
| Сбор: AC-тесты и команды проверки без `HAIPLANE_HUB_*` и без секретов в env | job `test` (код ветки) | только `HAIPLANE_HUB_CI_READ_TOKEN` (роль `ci_reader`: читает карточку задачи своего проекта) |
| Передача | артефакт `hub-ci-results-<run_attempt>` | данные: `results.json`, `audit.json` |
| Отправка отчёта и черновиков аудита | `ci-report.yml` на `workflow_run`, всегда с default-ветки | `HAIPLANE_HUB_CI_TOKEN` (роль `ci_runner`), `HAIPLANE_HUB_CI_AUDIT_TOKEN` (роль `ci_auditor`) |
| Отчёт о выкате | job `deploy` (только `main`) | `HAIPLANE_HUB_CI_TOKEN` |

`ci-report.yml` берёт факты о прогоне (коммит, id прогона, попытку, путь
workflow, событие, репозиторий ветки, итог) из события GitHub, а не из
артефакта. Артефакт читается в памяти по именам, с пределами (архив до 5 МБ, до
10 файлов, распакованное до 20 МБ), без ссылок и без путей вне корня. Строки из
него идут только в тело запроса к хабу. Черновики аудита зависимостей
заводятся только для `push` в `develop` и `main`.

Хаб сохраняет происхождение отчёта (`run_id`, `run_attempt`, `workflow_path`,
`event`, `head_repository`, `run_conclusion`, `artifact_id`, `artifact_digest`).
Сверку происхождения с GitHub делает хаб (#1687, раздел ниже).

### Порядок выката — строго такой

Default-ветка репозитория — **`main`**. GitHub запускает `workflow_run` из
default-ветки, поэтому `ci-report.yml` начинает работать только после того, как
он попал в `main`. Отсюда порядок:

- (a) Гейт `ci_before_submit` переводится в `warn` (политика проекта), пока
  отчёты не идут.
- (b) Слияние задачи, авторелиз в `main` и деплой. После этого роли `ci_reader`
  и `ci_auditor` созданы миграцией старта, а `ci-report.yml` лежит в `main`.
- (c) Владелец создаёт ключи, environments и секреты (шаги 1–5 ниже).
- (d) Уборка секретов уровня репозитория (шаг 6).
- (e) Живая проверка — канарейка AC-6 (шаг 7).
- (f) Гейт `ci_before_submit` возвращается в `require`.

Значения ниже — подстановки. Настоящие ключи не записываются ни в документы, ни в
ленту, ни в логи; вывод команд, который их содержит, не копируется.

1. **Принципалы и ключи в хабе.** Принципалов заводят через REST (в
   `oc-hub admin agents create` роли пока только `agent` и `watcher`):

   ```
   POST /api/admin/principals  {"kind": "service", "username": "<имя-читателя>", "role": "ci_reader"}
   POST /api/admin/principals  {"kind": "service", "username": "<имя-аудитора>", "role": "ci_auditor"}
   oc-hub admin keys create --principal <имя-читателя> --name ci-read --project default
   oc-hub admin keys create --principal <имя-аудитора> --name ci-audit --project default
   ```

   Ключ без `--project` эти роли отклоняют: режима «без области» у них нет.
   Ключ аудитора заводит только простые черновики без родителя и без `project`,
   они всегда попадают в проект `default`. Ключ показывается один раз; его сразу
   кладут в секрет по шагам 2–3, минуя чат и файлы. Ключ `ci_runner` (отчёт) не
   меняется.
2. **Environment `hub-report`** (Settings → Environments → New environment):
   `Deployment branches and tags` → `Selected branches and tags` → правило
   только для `main`, без тегов. Секреты environment: `HAIPLANE_HUB_CI_TOKEN`
   (текущий ключ `ci_runner`), `HAIPLANE_HUB_CI_AUDIT_TOKEN` (ключ `ci_auditor`).
3. **Секрет репозитория** `HAIPLANE_HUB_CI_READ_TOKEN` — ключ `ci_reader`.
   `HAIPLANE_HUB_URL` остаётся секретом репозитория.
4. **Environment `production`**: `Deployment branches and tags` → `Selected` —
   только `main`, без тегов. Секреты, которые читает job `deploy`, переезжают в
   него: `HAIPLANE_HUB_CI_TOKEN`, `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_USER`.
5. **Проверить правила веток** обоих environments (`gh api
   repos/<владелец>/<репозиторий>/environments/<имя>` — смотреть
   `deployment_branch_policy` и список политик, значений секретов там нет).
6. **Убрать секреты уровня репозитория (и организации), которые переехали:**
   `HAIPLANE_HUB_CI_TOKEN`, `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_USER`
   (`gh secret delete <ИМЯ> --repo <владелец>/<репозиторий>`), а также
   устаревшие репозиторные секреты со старым префиксом имени продукта — токен
   CI и URL хаба. Делать после шагов 2–5: раньше — деплой и отчёты останутся
   без ключа. Проверка, без значений: `gh secret list --repo <владелец>/<репозиторий>`
   не содержит этих имён; `gh secret list --env hub-report` и `--env production`
   содержат свои.
7. **Живая проверка (AC-6 задачи).** На ветке-канарейке `workflow_dispatch` CI с
   шагом в job `test`, который печатает *длину* `HAIPLANE_HUB_CI_TOKEN`, и двумя
   добавленными job — с `environment: hub-report` и `environment: production` —
   которые печатают длину секрета. Ожидается: в job `test` длина 0; оба job с
   environment не допущены правилом веток (GitHub пишет отказ по правилу
   развёртывания, ни один шаг не выполнен); отчёт по канарейке пришёл в хаб от
   `ci-report.yml` с происхождением; после `push` в `main` пришёл отчёт о выкате.
   Канарейку удалить после проверки.

Пока шаги 1–3 не сделаны, отчёты CI не доходят до хаба: `ci_before_submit` в
режиме `require` отвечает «нет отчёта» явно — поэтому до (f) он стоит в `warn`.
Откат: вернуть `HAIPLANE_HUB_CI_TOKEN` секретом репозитория и откатить коммит
задачи.

Репозитории-спутники используют action `hub-ci-report` с `hub-token` по-старому
(отправка из job ветки); перевод их на эту схему — отдельная задача.

## Хаб сверяет отчёт CI с GitHub (#1687)

Отчёт CI — доказательство, только если хаб через GitHub (здесь — только
читает; тот же токен хаба пишет при мерже и создании PR, см.
`docs/agent-context/invariants.md`, «Личность вливания», #1708) подтвердил: попытка `run_id`/`run_attempt` существует в репозитории проекта,
это workflow `ci.yml`, её `head_sha` равен `head_sha` отчёта, артефакт
`hub-ci-results-<попытка>` один, его id и digest совпадают, а содержимое
артефакта (результаты AC, проверки, validation, мутации, baseline) равно телу
отчёта. Зелёное доказательство требует `conclusion = success` и `lint`,
`format`, `types`, `tests` = `pass`. Неподтверждённый отчёт хранится и
показывается («CI-отчёт не подтверждён: <причина>»), но не пишет AC и
validation и не проходит `ci_before_submit=require`.

Текущая попытка коммита — та, что запущена позже всех среди всех прогонов
`ci.yml` на нём, включая перезапуск, о котором никто не сообщил. Доказательства
(результаты AC, validation, baseline, мутации) принадлежат попытке, которая их
прислала; при смене текущей попытки или её доверия они снимаются. Если GitHub
недоступен, подтверждения «сейчас» нет: `unverified(forge_unavailable)`,
доказательства сняты (прошлое подтверждение лежит в истории попыток, но не
служит доказательством). Поллер повторяет проверку каждые 5 минут до 6 часов,
потом ответ окончателен до нового отчёта; сверка в тике поллера ограничена по
времени, а после неудачного обращения GitHub 60 секунд не спрашивается.

Отчёты, записанные до выката и называющие прогон и артефакт (#1686), миграция не
хоронит: каждый ставится в очередь на сверку (попытка без проверки), поллер её
делает. Отчёты без названного прогона остаются `unverified(legacy)`, как и
записанные из них результаты AC и validation. Сколько задач в работе это
затрагивает — запрос в конце раздела.

### Порядок выката #1687 — владелец

Значения ниже — подстановки; токены не записываются ни в документы, ни в ленту.

- (a) **До слияния** проверить, что токен хаба к GitHub (он пишет — мержит PR,
  создаёт PR, диспатчит CI; для этой проверки достаточно чтения: fine-grained —
  *Actions: Read*; classic — `repo`) умеет скачивать артефакт. Без
  этого каждый отчёт станет `unverified(forge_unavailable)`. Команда запускается
  на сервере хаба под пользователем службы, окружение берётся из того же файла,
  что и у службы, и печатает только код HTTP и размер — токен не выводится:

  ```
  sudo systemd-run --quiet --pipe --wait --collect \
    --uid=<пользователь-службы-хаба> -p EnvironmentFile=<файл-окружения-службы-хаба> \
    sh -c 'd=$(mktemp -d) && gh api repos/<владелец>/<репозиторий>/actions/artifacts/<id-артефакта>/zip \
      >"$d/a.zip" 2>"$d/err"; rc=$?; \
      if [ $rc -eq 0 ]; then echo "HTTP 200"; else grep -o "HTTP [0-9][0-9][0-9]" "$d/err" | head -1; fi; \
      echo "size=$(wc -c <"$d/a.zip")"; rm -rf "$d"'
  ```

  `<id-артефакта>` — любой свежий `hub-ci-results-<N>` недавнего прогона
  (`gh api repos/<владелец>/<репозиторий>/actions/runs/<id-прогона>/artifacts`,
  в ответе поле `id`). Ожидается `HTTP 200` и размер больше нуля; `HTTP 403`/`404` —
  прав токена не хватает, выкатывать нельзя.
- (b) **На время выката** гейт `ci_before_submit` стоит в `warn` (политика
  проекта), чтобы неподтверждённый отчёт не останавливал сдачи, пока сверка
  проверяется вживую.
- (c) **После деплоя** дождаться первого живого отчёта и убедиться, что он
  `verified` (в брифе сдачи `ci_run_report.trust = verified`, либо
  `trust`/`trust_reason` в ответе приёма отчёта). Если пришло `unverified` —
  причина названа (`forge_unavailable` — права токена из пункта (a);
  `body_mismatch`/`artifact_mismatch` — расхождение отчёта и артефакта). Только
  после первого `verified` вернуть `ci_before_submit` в `require`.

Запрос для прода — сколько задач в работе затрагивает миграция (отчёт о закреплённом
коммите называет прогон и артефакт и будет проверен, против тех, что остаются
`legacy`); выполняется только на чтение:

```
SELECT t.status,
       SUM(COALESCE(json_extract(r.provenance, '$.run_id'), '') != ''
           AND COALESCE(json_extract(r.provenance, '$.run_attempt'), '') != ''
           AND COALESCE(json_extract(r.provenance, '$.artifact_id'), '') != ''
           AND COALESCE(json_extract(r.provenance, '$.artifact_digest'), '') != '') AS queued_for_check,
       SUM(NOT (COALESCE(json_extract(r.provenance, '$.run_id'), '') != ''
           AND COALESCE(json_extract(r.provenance, '$.run_attempt'), '') != ''
           AND COALESCE(json_extract(r.provenance, '$.artifact_id'), '') != ''
           AND COALESCE(json_extract(r.provenance, '$.artifact_digest'), '') != '')) AS legacy_only
FROM tasks t
JOIN ci_run_reports r ON r.task_id = t.id AND r.head_sha = t.submission_sha
WHERE t.status IN ('running', 'review') AND json_valid(r.provenance)
GROUP BY t.status;
```

Выполнять нужно до деплоя (колонки `provenance` достаточно): число в
`queued_for_check` — задачи, чей отчёт поставит в очередь миграция.

## CSRF для cookie-сессий (#1664)

Изменяющий запрос с cookie-сессией (веб-формы и REST) проверяется одним
middleware. Клиенты с `Authorization: Bearer` (агенты, CI, MCP, `oc-hub`)
токен не передают.

- `HAIPLANE_HUB_CSRF_SECRET` — необязательная переменная окружения с ключом
  токена. Без неё ключ лежит в файле `csrf_secret` (права 0600) рядом с базой;
  потерять его можно только вместе с каталогом данных. Пока ключ не из env,
  `/health` показывает `csrf_key_source` и `csrf_warning`. Значение в
  документы и логи не записывается.
- `HAIPLANE_CSRF_MODE` — `off`, `warn` или `require`; по умолчанию `warn`.
  `warn` пропускает запрос и пишет событие `csrf_would_reject`; число таких
  событий за сутки — `csrf_would_reject_24h` в `/health`. Неизвестное значение
  читается как `warn`.
- Переключение в `require` — владелец, после задачи #1665 (токен во всех
  формах и HTMX-запросах) и недели без событий `csrf_would_reject`.
- Origin сверяется с `HAIPLANE_HUB_URL`: он должен совпадать с публичным
  адресом хаба, иначе в `warn` пойдут события `origin_mismatch`.

## Мутации и baseline в CI: по событию, а не на каждом обновлении ветки (#1606)

Шаги «Mutations of changed functions» (~9,5 мин) и «Red-test baseline» (~2–3
мин) совещательные: гейт доставки их исход не читает. Раньше они шли на каждом
`pull_request`, и каждое обновление ветки гейтом (подтянул базу) или автором
стоило 13–22 мин. Теперь решение принимает шаг `evidence` в `ci.yml` по событию
GitHub, без обращения к хабу:

| Событие | Мутации и baseline |
|---|---|
| `workflow_dispatch` task-ветки (ручной прогон исполнителя до сдачи; прогон от гейта #1197 тоже) | считаются, база — `origin/<base_ref>` либо `origin/develop` |
| `pull_request` `opened` / `reopened` task-ветки | считаются |
| `pull_request` `synchronize` | пропущены, причина — одной строкой в логе |
| не-task PR: `develop`→`main`, `main`→`develop`, `dependabot/*`, прочие не `task-*`; `push` | пропущены, причина — строкой в логе |

Test, AC и validation идут на каждом событии как раньше. `deploy`
(`needs: test`), Compose и `treedup` не менялись: `treedup` может
переиспользовать успешный PR-прогон с пропущенными мутациями, потому что `Test`
в нём выполнен, а красный `Test` не даёт успешный workflow.

### Усыновление evidence dispatch-прогона (#1919)

Исполнитель запускает `workflow_dispatch` до сдачи, хаб открывает PR при сдаче:
оба прогона стоят на одном `head_sha`, и мутации с baseline считались дважды
(~10,5 мин). Теперь на `pull_request` `opened`/`reopened` task-ветки шаг
`adopt` в job `treedup` (`scripts/adopt_evidence.py decide`, только stdlib,
`python3 -I`) ищет успешный dispatch-прогон `ci.yml` на том же `head_sha`.
Условие: job `evidence` источника зелёный, артефакт `hub-ci-evidence` жив,
состояния файлов несут информацию (мутации `ran`/`no_changed_functions`/`no_tests`,
baseline `ran`/`no_tests`), и `merge_base == base_tip ==` первому родителю
merge-коммита PR-прогона (`HEAD^1`; событийный `base.sha` может отставать), а
дерево merge-коммита равно дереву головы. Любое сомнение или сбой — прежний
пересчёт, джоб не краснеет. При успехе тот же шаг пишет оба файла в
`adopted-evidence/` с ключом `adopted_from_run` внутри блока (не в `provenance` и
не в `results.json`), а следующий шаг заливает их как `hub-ci-evidence` ЭТОГО
прогона; выход `adopt` равен `true` только если залив удался (иначе — пересчёт).
Тогда ноги мутаций, baseline и слияние пропускаются. Брифинг ревью показывает
«усыновлено из dispatch-прогона N (со слов прогона)». Срок хранения
`hub-ci-evidence` — 3 суток.

### Мутации матрицей ног (#1921)

Серия мутаций шла последовательно под одним бюджетом 540 с, почти всегда
выбранным целиком (570–690 с на критическом пути). Теперь это матрица ног
(`mutation_legs`, число ног — `matrix.leg`, сейчас 3): нога `i` из `N` берёт
мутантов, чей номер в одном глобальном порядке равен `i-1` по модулю `N`
(`mutation_changed.py --shard i/N`; порядок — по ключу самого мутанта: файл,
границы, оператор, вхождение, потому что cosmic-ray отдаёт мутантов случайно).
Бюджет серии ноги — `540/N` с, не меньше 60; baseline имеет свой потолок
(`--baseline-timeout 540`). Red-test baseline — отдельный job `baseline`, он не
ждёт ног. Отчёты ног и baseline уходят промежуточными артефактами
(`hub-ci-mutations-leg-<i>`, `hub-ci-baseline`, имена вне префикса
`hub-ci-results-`); job `evidence` («Mutations and red-test baseline», только
stdlib, ничего не ставит) складывает их `scripts/merge_mutation_legs.py` в один
`mutation-report.json` и заливает `hub-ci-evidence`. Нехватка ноги, чужой
`head`/`merge_base`, красный baseline на одной ноге — явный `error` /
`baseline_red` с причиной, не «ran». Имена шагов в ногах и в baseline не
менялись: хаб считает минуты шага по ИМЕНИ и складывает по всем job
(`ci_timing.summarize`). Перезапуск упавшей ноги (`gh run rerun --failed`)
создаёт новую попытку: до её отчёта хаб даёт `current_attempt_incomplete`.

Как это доходит до хаба. Репортёр получает исходы шагов. Шаг не запускался
(`skipped`) — ключа `mutations`/`baseline` в отчёте нет, и хаб оставляет то, что
уже сохранил для **этой попытки** (REST различает «ключ не прислан» и «прислан»,
замена идёт атомарно внутри `ON CONFLICT`). С #1687 так только внутри одной
попытки: доказательство принадлежит попытке, которая его прислала, и более
новая попытка того же коммита **не наследует** baseline и мутации прежней. Шаг
шёл, но валидного файла нет
(timeout, битый JSON) — блок `state=error` с причиной, он заменяет сохранённое.
Каждый присланный блок несёт `provenance` (`run_id`, `run_url`, `event`, `at`);
бриф показывает его рядом с блоком, а блок без него — «прогон неизвестен».

Контракт пересдачи. Новая голова уже открытого PR (в том числе первая сдача при
заранее открытом PR) получает мутации и baseline, только если исполнитель
запустил `workflow_dispatch` до сдачи: `gh workflow run ci.yml --ref <ветка>`.
**Последняя** попытка CI на закреплённом коммите должна сама нести baseline:
если после dispatch-прогона на тот же sha прошёл ещё один прогон (перезапуск,
`synchronize`), и в нём шаг baseline не шёл, текущей становится он, а baseline
dispatch-прогона перестаёт быть доказательством. Тогда `bug_red_test=require`
откажет — лечится повторным `gh workflow run ci.yml --ref <ветка>` и ожиданием
его отчёта; после него последней оказывается попытка с baseline.
Иначе бриф пишет «не получено» — это не pass. Баг-задача с
`bug_red_test=require` без baseline получает прежний отказ 422, поэтому для неё
ручной прогон до первой сдачи обязателен всегда. Если пересдачи начнут массово
приходить без мутаций, вернуть мутации на `synchronize` task-веток либо требовать
dispatch-отчёт при сдаче (условие пересмотра задачи #1606).

## Параметры варианта модели исполнителя (#1769)

`HAIPLANE_EXECUTOR_MODEL_PARAMS` — пары `id=value` через запятую, например
`context=256k,reasoning_effort=high,fast=false` (для grok-4.7). Контракт Cursor
требует полный набор параметров варианта: список из каталога `GET /v1/models`.
Пусто (по умолчанию) — заказ исполнителя без `params`, вариант по умолчанию у
Cursor (у части моделей это Fast).

- Params уходят во все пять дверей заказа облачного исполнителя (запуск,
  починка, слияние, продолжение, «только сдай»). Слот k8 их не касается.
- HTTP 400 не по лимиту на заказ с params — один заказ без них на весь заказ;
  после успеха в ленте задачи alert с названием сброшенных params. Повторы
  429 и `rate_limit_exceeded`/`usage_limit_exceeded` идут с теми же params.
- `executor_runs.model` хранит фактический вариант (`grok-4.7 context=256k,...`),
  после сброса — голую модель.

## Git-доступ workspace (провижининг проектов, #347/#348)

Хаб клонирует workspace проектов сам (`POST /api/projects/{id}/provision`,
кнопка **Provision** на `/projects`, MCP `hub_provision_project`). Для этого
пользователю, под которым работает сервис хаба, нужен git-доступ к репозиторию
проекта. **Публичные репозитории читаются анонимно по https — настройка не
нужна** (#377: короткая форма `owner/repo` сначала пробует https, затем ssh).
Для приватных — один из двух вариантов:

1. **Deploy key (рекомендуется для приватных репо):** ssh-ключ
   `~/.ssh/id_ed25519` пользователя сервиса добавлен как Deploy key
   репозитория (read-only достаточно). `git_ops` подхватывает его
   автоматически через `GIT_SSH_COMMAND`.
2. **gh auth:** `gh auth login` под пользователем сервиса (тогда repo можно
   указывать как `owner/repo`, https-доступ пойдёт через gh-креды).

Проверочная команда (под пользователем сервиса):

```bash
sudo -u <svc-user> git ls-remote git@github.com:<owner>/<repo>.git HEAD
```

Именно её эквивалент хаб выполняет перед клоном: если доступа нет, провижининг
вернёт `provision_status=error` с текстом ошибки ls-remote — это штатная
диагностика, а не падение.

Онбординг проекта за минуту: создать проект на `/projects` (repo +
workspace path) → провижининг стартует автоматически (или кнопкой
Provision) → привязать эпик (`project` при создании эпика, #346) — задачи
проекта едут по его репозиторию и веткам.

### HAIPLANE_WORKSPACE_REPO (#378)

Нужен ТОЛЬКО для pair-конвейера задач default-проекта (подготовка веток на
сервере). Провижининг проектов и git-операции проектных workspace работают
без него. Если переменная не указывает на git-клон, pair_start для
default-задач вернёт читаемую 422-ошибку с подсказкой.
