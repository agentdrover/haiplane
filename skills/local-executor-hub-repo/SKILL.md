# local-executor-hub-repo — локальный исполнитель в репозитории Haiplane Hub

Для кого: исполнитель с локальной средой (Claude Code или Codex на машине
владельца или на узле агентов), у которого есть авторизованный `gh`, право
запуска workflow и, возможно, `codex`. Репозиторий — `agentdrover/haiplane`.
Облачный исполнитель Cursor читает `executor-pair-discipline`; этот навык его
дополняет для локальной среды, а всё из `executor-pair-discipline` в силе.

**Как читать.** Навык разбит по этапам. Открой раздел этапа, на котором ты
сейчас, и держи в работе только его. Перешёл на следующий этап — перечитай
его раздел заново, а не по памяти.

Каждое правило ниже стоило лишнего цикла CI или ревью в 06–12.10.2026.

## Этап 1. Работа над кодом

- **Мутация на красном наборе ничего не доказывает.** Сначала базовый прогон
  зелёный, потом мутация, потом имя упавшего теста — ровно test_ref этого AC.
  Имя сверяй по полному выводу, не по обрезанному `head`/`tail`.
  Серию гоняй без байткода: `PYTHONDONTWRITEBYTECODE=1`, `-p no:cacheprovider`.
- **Хуки не обходить.** Никаких `--no-verify` и `core.hooksPath=/dev/null`,
  в том числе для промежуточного коммита. Хук режет — исправь причину.
  Каждый коммит, merge-коммит тоже, кончается строкой Co-Authored-By.

## Этап 2. Перед сдачей

1. **Полный `make check`**, каждый шаг по коду возврата: lint, types (mypy),
   budget, security (bandit), secret_scan, test. Одних тестов мало.
2. **Влей свежую базу задачи** (имя — из pair-start; для хаба это `develop`)
   обычным merge, без rebase и force-push, и прогони проверки снова. CI у PR
   проверяет слияние с базой, а не твою ветку: ветка бывает зелёной, а PR —
   красным (бюджет сложности после слияния).
3. **Конфликт слияния** разрешай по смыслу: сверь общий предок и обе версии.
   Если обе стороны добавили независимые блоки (поля модели, тесты), сохрани
   оба. `git checkout -m <файл>` — только чтобы намеренно вернуть маркеры,
   он стирает ручное разрешение. После — тесты затронутого поведения и
   полный `make check`. В summary назови, с какой задачей был конфликт и где.
4. **Пуш, потом CI, потом отчёт CI в хабе.** Пуш полным refspec, затем
   `git ls-remote origin <ветка>` совпадает с `git rev-parse HEAD`. Дальше:
   `gh workflow run ci.yml --ref <ветка> --repo agentdrover/haiplane`;
   найди прогон по `--commit "$SHA" --event workflow_dispatch`;
   `gh run watch <id> --exit-status`. С #1686 (12.10) отчёт хабу шлёт
   **отдельный** прогон `ci-report.yml` (workflow_run с main) через несколько
   минут после конца CI ветки: дождись его завершения для этого SHA
   (`gh run list --workflow ci-report.yml --limit 5`) и только потом сдавай.
   С #1687 (13.10) хаб сверяет отчёт с GitHub (попытка, ci.yml, head_sha,
   артефакт и его digest): гейт пропускает только отчёт с trust=verified.
   Перезапуск того же коммита делай полным прогоном — baseline между
   попытками не наследуется, без него откажет гейт красного теста.
   Сдавай ровно этот sha.
   С #1862 на проектах с `ci_before_submit` не `off` и контрактом CI (GitHub)
   хаб сам просит прогон на новой голове ветки задачи в `running` и пишет в
   ленту «запрос CI принят для ветки …», затем «CI на sha …: <итог> (run …,
   попытка N)» после подтверждения отчёта. Облачный исполнитель без `gh` ждёт
   эти записи и не просит запуск текстом. Локальный исполнитель с `gh`
   запускает CI как раньше: хаб выдерживает окно grace (по умолчанию 120 с) и
   видит чужой прогон workflow контракта — второй запрос не делает. На проектах
   вне области (`off`, нет контракта, не GitHub) — ручной запуск, как выше.
5. **Гейт CI.** Режим `ci_before_submit` читай в `working_rules.project_policy`.
   При `require` хаб требует сохранённый зелёный отчёт CI по этому sha
   (validation pass, нет красных и потерянных тестов AC); иначе сдача
   получит 422 `ci_before_submit_unproven`. Success в GitHub отчёт не
   заменяет. Отказ разбери по `cause` (no_report | red | validation_not_pass |
   malformed): `no_report` сразу после CI — обычно ci-report.yml ещё не
   дошёл, подожди его. Неподтверждённый отчёт: причина в брифе
   «CI-отчёт не подтверждён: <причина>». Вслепую не повторяй.
6. **Второй ревьюер Codex — по одному правилу (#1702).** Это единственное
   место, где правило записано; `hub-submit-task` §5.4 только ссылается сюда.
   Codex нужен, если верен хотя бы один признак:
   - класс риска задачи R2 или выше (`risk_class` в `hub_task_status`);
   - класс не посчитан или нечитаем: неизвестный класс не равен низкому (#582);
   - дифф `origin/<база>...HEAD` касается решателя одобрения — путь из
     `APPROVAL_DECIDERS` (`hub/services/auto_approve.py`);
   - дифф ДОБАВЛЯЕТ код с маркером процессной поверхности из
     `_PROCESS_SURFACES` (`hub/services/review_dispatch.py`): подпроцессы,
     таймауты и отмена, воркспейс и ветки, конкурентный доступ. Отбор — как у
     `process_surface_reasons` (там же): считаются только добавленные строки
     вне комментариев, сгенерированные файлы отброшены; упоминание маркера в
     тексте или в удалённой строке поверхностью не считается;
   - среди рисков задачи есть `kind=security`, любой серьёзности.

   Признак поверхности важнее класса: решатель или процессная поверхность
   дают «нужен» и при R0. Нет ни одного признака, но класс известен и ниже R2 —
   Codex не нужен; запускать его вне правила можно, это решение исполнителя,
   но его круг в метрику «нужен» не входит. Порог R2 выбран владельцем 15.10
   (на R2 Codex нашёл два настоящих P2 в #1694); это порог правила процесса,
   он НЕ равен порогу профиля deep у хаба (`_DEEP_FROM_CLASS`, R3), и код хаба
   правило не проверяет. Команды `codex` на машине нет — назови это в отчёте и
   не подменяй ревью чем-то другим.

   | Случай | Решение | Причина |
   |---|---|---|
   | R1 + `kind=security` | нужен | признак security важнее класса |
   | R1 + правка `hub/services/auto_approve.py` (решатель) | нужен | `APPROVAL_DECIDERS` важнее класса |
   | R0 + добавлена строка с `asyncio.wait_for(` | нужен | процессная поверхность важнее класса |
   | R2 без решателей, поверхностей и security | нужен | класс R2 — порог |
   | `risk_class` пуст или нечитаем, признаков нет | нужен | неизвестный класс |
   | R1, `wait_for(` только в комментарии или в удалённой строке | не нужен | считаются добавленные строки кода |
   | R1, только документация, security нет | не нужен | признаков нет, класс ниже R2 |

   Запуск при «нужен», если `command -v codex` находит команду:
   `codex exec --sandbox read-only --ephemeral -C <worktree> -o <файл>
   "<ревью диффа origin/<база>...HEAD по задаче, находки P1/P2/P3 с
   файл:строка>" < /dev/null`, в фоне, без timeout. P1 и P2 исправь одним
   кругом, затем одна сдача; исход каждой находки назови в summary. Codex
   получает доступ только на чтение и не видит токенов исполнителя.

   К этому же правилу относятся три требования к кругам ревью (#1866); второго
   правила второго ревью они не создают.
   - **Свежий взгляд до пуша.** Перед пушем отдай `git diff origin/<база>...HEAD`,
     цель и AC ревьюеру в чистом контексте: `codex exec` (запуск выше) или,
     когда `codex` на машине нет и Codex не обязателен по признакам выше, —
     субагент без истории работы. Подмена обязательного Codex субагентом
     остаётся решением оркестратора, как описано выше. Ревьюер даёт находки
     P1/P2/P3 с `файл:строка`, у каждой — класс дефекта и все места класса в
     диффе. P1 и P2 исправь до пуша; неисправленное назови в summary. В отчёте
     сдачи укажи проверенный sha и исход каждой P1/P2.
   - **Класс ошибки на доработке.** Если находка называет класс дефекта, чини
     все места этого класса в пределах области задачи, а не только названное
     место. Места вне области остаются `out_of_scope`, как сейчас.
   - **С третьего возврата — смена подхода.** После третьего `changes_requested`
     по задаче (`review_cycle` ≥ 3) до кода запиши в ленту: почему подход
     порождает новые находки и какой другой подход берёшь (пример: белый список
     вместо запретов, один писатель вместо дедупликации, убрать функцию вместо
     фильтра). Код — после записи.

## Этап 3. Сдача и после неё

1. **Одна проверка после сдачи**, без опроса: `gh pr checks <PR>` и
   `mergeStateStatus`. Запиши результат в отчёт и заверши прогон.
   CLEAN значит только «GitHub не видит препятствий»; доставку подтверждает
   хаб. DIRTY или CONFLICTING — назови это в отчёте; причину проверь, не
   считай любое DIRTY движением базы.
2. **Изменил авторский код после сдачи — новый коммит, пуш и новая сдача**
   (новое поколение). Влить базу после APPROVED может сам гейт без нового
   ревью; исполнитель сам такое исключение не объявляет и после APPROVED
   базу не вливает без заказа.
3. **После APPROVED не вызывай `report_done`** и не пересдавай без изменения
   работы: поллер доставляет сам после гейтов. В 09.2026 параллельные
   done-отчёты роняли гейт в `database is locked` (#1428). Новый заказ на
   исправление (`ci_failed`, `stale_approval`) исполняй обычным циклом.

## Отчёт оркестратору

Кратко: sha сдачи, PR, CI dispatch, прогон ci-report.yml и принят ли отчёт
хабом, PR checks, мутации по AC (с именем упавшего теста), находки Codex и
их исходы, отклонения от постановки и почему. Нарушения правил (обход хука,
лишний коммит, пропущенный шаг) называй сам.
