Pair mode: git policy

Gap #43 закрыт: где живёт git, кто push, что делает hub при hub_pair_start.

Сценарий 1 — Local clone (hub и Cursor на одном каталоге)

риск OPENCLAW_WORKSPACE_REPO = каталог в Cursor. При dirty worktree hub_pair_start вернёт 422 — commit/stash до старта. См. pair_prepare_branch в коде.

  1. Commit или stash до hub_pair_start.
  2. Plan: update или поле plan в pair-start.
  3. hub_pair_start(task_id, assigned_agent=...) → статус running, в задаче поле branch.
  4. Сверить git branch с branch в хабе; при расхождении — merge/checkout вручную.
  5. Коммиты в task-<id>/<slug>, push, PR в develop.
  6. hub_report_done; human gate / CI #38 ✓.

Сценарий 2 — Server workspace (hub на agenthai, Cursor на ноутбуке)

OPENCLAW_WORKSPACE_REPO на сервере; pair-start создаёт branch там. Локальный Cursor не переключается сам.

  1. Локально: git fetch, git checkout -b task-<id>/<slug> (имя из задачи в hub).
  2. Работа и коммиты на ноутбуке.
  3. git push -u origin HEAD — CI видит код только после push.
  4. PR → review → merge по repository-rules.md.

Что hub не делает в pair mode

  • Не вызывает oc-dev-dispatch (job_id остаётся пустым).
  • Не синхронизирует автоматически server clone ↔ laptop (out of scope #43).
  • Не заменяет push/PR человека или агента в Cursor.

Pair: вопрос до pair-start (B7)

Gap #39 закрыт: агент в Cursor может уточнить требования, пока задача ещё в open.

  1. После approve задача в open, job_id пустой.
  2. hub_ask_question(task_id, question=...) → needs_info (не 400).
  3. Человек: hub_answer_question — resume=true без dispatch #40 ✓.
  4. Далее hub_pair_start или работа по обновлённому scope.

На headless running с job_id поведение hub_ask_question без изменений.

Pair: ответ без headless dispatch (B8)

Gap #40 закрыт: после needs_info pair-задача не уходит в oc-dev-dispatch.

  1. Pair = пустой job_id (до или после hub_pair_start).
  2. hub_answer_question(..., resume=true) → open (до pair-start) или running (если есть branch), без job_id.
  3. resume=false → только answer update, статус open.
  4. Headless с job_id: resume=true по-прежнему re-dispatch.

Pair: MCP hub_report_done (B9)

Gap #44 закрыт: ответ MCP отражает фактический status, без «should now be completed».

  • open/running → status unchanged или ci_check (pair conveyor).
  • pending_report → completed с явным текстом.

Pair: claim / release (B10)

Gap #41 закрыт: один активный исполнитель на задачу.

  1. hub_claim_task(task_id, agent=..., session_id=...) — open → claimed.
  2. Повторный claim другим agent/session → 409.
  3. hub_release_task — claimed → open, audit update.
  4. Далее hub_pair_start (свой claim) или release.

Inbox: «мои задачи» (B11)

Gap #42 закрыт: персональный фильтр Inbox и list API.

  1. Web Inbox: поле My tasks → query mine=<person> (owner или claim holder).
  2. REST: GET /api/tasks?human_owner=, claimed_by=, mine=.
  3. MCP: hub_list_tasks(human_owner=..., claimed_by=..., mine=...).
  4. CLI: oc-hub list --owner, --claimed-by, --mine.
