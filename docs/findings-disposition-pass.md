# Разбор находок: как пройти очередь и что считать результатом (#1171)

Механика разбора построена целиком и до сентября 2026 не была использована ни
разу: 131 подтверждённая находка без ответа, `dispositions.judged=0`,
`precision=null`, `by_profile` — пустой список. Разрыв не в инструменте, а в
его применении, и этот документ описывает применение.

## Зачем

`findings_confirmed` — это ВНУТРЕННЕЕ согласие верификаторов одного прогона:
харнесс проверяет собственную домашку. `precision` — первое ВНЕШНЕЕ число о
качестве машинного ревью: не «сколько нашли», а «сколько из найденного
оказалось правдой». Без него нельзя ни выбрать между дорогим и дешёвым
профилем, ни решить, где модель пора заменить детерминированной проверкой.

## Кто судит

Только человек. `POST /api/tasks/{id}/finding-dispositions` требует
human-или-admin (#876, правило 1): агент, чью работу ревьюили, не может
объявить находку ложной — это ревьюируемый, оценивающий своего ревьюера.
Автоматизации у этого шага нет и по контракту не будет.

## Граница, от которой зависит precision

Берётся из модуля дословно и стоит у самих кнопок:

* **исправлено** (`fixed`) — дефект был, его починили;
* **ложняк** (`false_positive`) — описанного дефекта В КОДЕ НЕТ;
* **неважно** (`wont_fix`) — дефект есть, чинить не будем.

`precision = (fixed + wont_fix) / judged`. Размывание границы между ложняком и
«неважно» смещает precision напрямую, поэтому перепроверка (ниже) смотрит
именно на неё.

## Что показывает очередь и чего она НЕ делает

`/findings` кладёт рядом с каждой находкой два ВХОДА:

* **факт касания** (#1039) — тронул ли последующий коммит названное место.
  Три ответа, не два: `touched` / `untouched` / `unknown`, и у `unknown`
  названа причина. Это про КОД, а не про дефект: коммит, тронувший строки, не
  равен починенному дефекту;
* **слово автора** (#911) — что автор сделал с находкой на пересдаче. Это
  ОТЧЁТ, а не суждение; хранится в своей таблице и в `dispositions.judged` не
  попадает ни одним путём.

Ни один переключатель не предустановлен ни по одному из этих входов. Находка,
оставленная «не размечено», остаётся неразмеченной: дефолтная диспозиция не
назначается ни при каком объёме очереди (#549).

## Порядок прохода

0. Снять снимок очереди — ПЕРЕД заходом и в тот же присест:
   `uv run python scripts/finding_queue_report.py snapshot`, вывод в тело
   задачи. Снимок и проход принадлежат одному актору и одному сидению:
   знаменатель, снятый неделю назад, меряет уже другую очередь.
1. Открыть `/findings` и выбрать категорию — они выстроены по убыванию числа
   находок. Заход идёт ОДНОЙ категорией: сто находок вперемешку — это то, как
   суждение к концу списка становится штампом.
2. Внутри выборки свежие отчёты идут первыми: свежую находку судить точнее,
   код ещё похож на тот, о котором писал ревьюер.
3. Находку, по которой факт `unknown` и судить не по чему, оставить
   неразмеченной. Она попадёт в строку отчёта «судить не по чему» с причиной.
4. Сохранение возвращает в ту же категорию и тот же проект.

## Числа

```bash
uv run python scripts/finding_queue_report.py snapshot          # знаменатель приёмки
uv run python scripts/finding_queue_report.py report --since-days 60
uv run python scripts/finding_queue_report.py recheck --salt <дата>
uv run python scripts/finding_queue_report.py recheck --salt <дата> --answers второй-проход.csv
```

* **Снимок** фиксирует список uid и число НА СТАРТЕ. Очередь пополняется
  каждым новым отчётом, и «разобрано 95% очереди» без снимка мерило бы гонку
  разбора с конвейером, а не разбор.
* **Сток и поток не складываются.** «В очереди за всё время N» — запас, он не
  оконный: находка, не отвеченная в апреле, не отвечена и сегодня. «Покрытие
  отчётов за окно: X из Y» — поток, и отчёт считается разобранным, только
  когда отвечены ВСЕ его подтверждённые находки. В одну дробь их не сводить.
* **Разбор печатается двумя срезами, и это тот же разлад стока и потока.**
  `practice_metrics` берёт диспозиции по дате ОТЧЁТА, поэтому суждение,
  вынесенное сегодня о находке из отчёта трёхмесячной давности, в оконный срез
  не попадает вовсе. «РАЗБОР ЗА ОКНО (N дней по дате ОТЧЁТА)» — то же число,
  что на странице метрик и в AC-4, **при том же N**. «РАЗБОР ЗА ВСЁ ВРЕМЯ» —
  там виден разбор накопленного запаса, который иначе читался бы как ноль на
  следующее утро после того, как весь сток разобрали.
* **Два разных дефолта окна, и это не опечатка.** У команды выше
  `--since-days 60` — окно приёмки #1171 («0 из 29 отчётов»). У страницы
  `/metrics`, у дайджеста и у `hub_practice_metrics` дефолт `90` — исторический
  и не менявшийся. Одинаковыми числа будут только при одинаковом N: сверять с
  `/metrics?since_days=60`, а не с голой страницей. Скрипт печатает это
  расхождение строкой под оконным срезом, когда окна не совпадают, чтобы
  «то же число» не сравнивали за разные периоды.
* **Число всегда с размером выборки.** Ниже 20 разобранных на срез скрипт
  печатает «недобор», а не цифру: две находки дают precision 1.0, и голая
  единица зовёт к решению, которого выборка не выдерживает (#1153).
* **Ключ `--no-evidence` не отменяет секцию, а называет пропуск.** Подсчёт
  доли `unknown` требует клонов задач; без него скрипт печатает «не считали
  (ключ `--no-evidence`)», а не убирает строку: исчезнувшая секция читается как
  «unknown нет» (#762).
* **Слепая перепроверка** — 10% разобранного, отобранные детерминированно по
  (uid, соль). Второе суждение выносится без первого перед глазами; ответы
  кладутся файлом `uid,disposition`. Расхождение выше 20% означает, что разбор
  был штампом, и не засчитывается. Сравнение идёт с ПЕРВЫМ суждением по uid:
  один uid встречается больше раза законно (лестница #879 на одной сдаче, две
  задачи с одинаковым содержанием находки — uid считается из содержания, без
  `review_id`), и взяв последнее, перепроверка сверяла бы второе суждение с
  третьим, а штамп на первом проходе остался бы невидим.

## Сторож

Очередь выше порога (`UNJUDGED_FINDINGS_ALERT_THRESHOLD`, по умолчанию 40)
поднимает событие `unjudged_findings_alert` с числом и ссылкой — один раз в
сутки, не на каждый проход поллера. То же число едет попутчиком в дайджесте
(#739), рядом с долгом категорий и человеческой очередью: это свойство
практики, а не активности автопилота за сутки, и дайджеста собой оно не
порождает.

Про precision сводка дайджеста говорит только то, что знает. Непустая очередь
и «precision не считается» — РАЗНЫЕ факты: precision это `real/judged` по
разобранным, и первая же диспозиция делает его числом, сколько бы находок ни
ждало рядом. Пока не разобрано ничего — «ни одной диспозиции ещё нет»; дальше
— ставка вместе с размером выборки и окном (#1153), со ссылкой на метрики.

## Условия пересмотра

* доля `unknown` в очереди выше 40% — судить по истории не на чем, разбор
  переезжает в момент фикса, а очередь списывается с названной причиной;
* расхождение слепой перепроверки выше 20% — разбор был штампом.
