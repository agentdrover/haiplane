# «session expired» после релиза: вызов MCP выполнен, ответ потерян

Спайк #1363, 24.09.2026. Код хаба не менялся.

| следующий шаг | статус на 24.09 |
|---|---|
| [#1364](https://agenthai.ru/tasks/1364) — MCP-транспорт хаба в stateless-режим | заведена из спайка, DoR пройден (readiness 96), владелец одобрил, статус running (REST /api/tasks/1364, 24.09) |

## Коротко

- Сессии MCP живут в словаре процесса. Рестарт при релизе их теряет.
- Первый вызов каждой клиентской сессии после рестарта получает от сервера
  404 `Session not found`. Инструмент при этом **не выполняется**.
- Claude Code сам переподключается и **один раз повторяет** вызов. Этот повтор
  доходит до сервера и **пишет**.
- Параллельно в клиенте работает фоновый цикл переподключения. Примерно через
  секунду он закрывает соединение, по которому идёт повтор. Агент получает
  `MCP server "<имя сервера хаба>" session expired` на уже выполненной записи.
- За 25.08–24.09 в логах клиента 281 такой автоповтор. 101 из них закрыт
  ошибкой «Connection closed». 70 из этих 101 пришлись на пишущие инструменты:
  агент получил ошибку, а запись прошла. Остальные 31 — чтения. У
  `hub_submit_for_review` закрыто 50 повторов из 60: она медленная (5–15 с) и
  почти всегда проигрывает гонку. Разрез приведён в таблице раздела 3.
- Сам клиент дублей не делает. Дубли делал агент, который вручную повторял
  вызов после ошибки: 11 наблюдённых двойных записей (8 сдач, 2 `report_done`,
  1 `hub_task_update`), все за 26.08–01.09. Список — в разделе 4.
- Выполненность записи зависит от того, где гонка оборвала повтор. 24.09 в
  07:42 `hub_task_update(1370)` вернул тот же «session expired», но запись
  **не прошла**. Её сделал только ручной повтор агента (раздел 4а). По тексту
  ошибки нельзя понять, прошла запись или нет.
- Рекомендация: перевести транспорт в stateless-режим (#1364). Нет сессии —
  нет 404, нет пути восстановления в клиенте и нет гонки. Правило «сначала
  `hub_task_status`, потом повтор» и ключ идемпотентности (#1059) остаются
  нужны и после stateless.

## 1. Где живут сессии

- `hub/mcp_server.py:153`: `InstrumentedFastMCP(...)` создаётся без
  `stateless_http`. По умолчанию в mcp 1.28.1 это `False`, то есть режим со
  сессиями.
- `hub/app.py:240`: `mcp_server.streamable_http_app()` создаёт
  `StreamableHTTPSessionManager`. Строка `hub/app.py:302` запускает его внутри
  lifespan приложения, `hub/app.py:3532` монтирует его в корень.
- `.venv/.../mcp/server/streamable_http_manager.py:90`: сессии хранятся в
  `self._server_instances: dict[str, StreamableHTTPServerTransport]`. Это
  живые anyio-задачи в памяти процесса. Внешнего хранилища SDK не
  предусматривает, `session_idle_timeout` по умолчанию `None`.
- `streamable_http_manager.py:336-341`: неизвестный id получает 404 и
  JSON-RPC `-32600 Session not found`. Ответ уходит **до** всякого разбора
  вызова.
- `deploy/remote-deploy.sh:42`: каждый релиз делает
  `systemctl restart haiplane-hub`, и процесс начинает с пустым словарём.
  Сервис работает одним процессом uvicorn (`hub/app.py:3541`), поэтому
  воркеров, которые не знают сессию друг друга, нет. Причина только в
  рестарте.

## 2. Опыт на локальном хабе (AC-1)

Скрипт: временный хаб на 127.0.0.1 с пустой базой. Клиент на Python SDK
(`mcp.client.streamable_http`). Шаги: открыть сессию, записать A через
`hub_task_update`, SIGTERM и новый старт процесса, послать `tools/call` с
**прежним** `Mcp-Session-Id`, посчитать строки в `task_updates`, открыть
новую сессию и повторить. Второй прогон — тот же хаб, где `stateless_http`
выставлен до построения приложения (лабораторный запуск, в код не входит).

| Шаг | stateful (как на проде) | stateless |
|---|---|---|
| запись A в живой сессии | ok, 1 запись | ok, 1 запись |
| вызов B со старым id после рестарта | **HTTP 404** `Session not found` | **HTTP 200**, результат |
| записей B после этого вызова | **0** | **1** |
| повтор B в новой сессии | ok, записей B = 1 | ok, записей B = 2 (повтор неидемпотентной записи) |

Вывод: после рестарта сервер сам ничего не выполняет по устаревшей сессии.
Записать может только повторный вызов в новой сессии. Stateless убирает 404
целиком. Последняя строка ещё раз показывает, что `hub_task_update` при
повторе пишет второй раз.

по `tool` и окну `[ts, ts+60s]`. Окно не различает авторов, поэтому это
верхняя граница, но нулей среди 70 нет.

## 5. Какие вызовы опасно повторять

Опасность одна для всех: агент получает ошибку и не знает, прошла ли запись.
Если прошла (раздел 3), ручной повтор делает дубль. Если нет (раздел 4а),
отказ от повтора теряет запись. Поэтому сначала читается состояние, и только
потом решается, повторять ли.

| инструмент | повтор после прошедшей записи | основание |
|---|---|---|
| `hub_task_update` | **вторая запись в ленте** | опыт раздела 2; #969 |
| `hub_report_done` | **второй `done` в ленте**; с `pending_report` возможно второе поколение (#1059) | #962, #1069; код `pending_report` не проверялся |
| `hub_submit_for_review` | тот же sha из `review` — без нового поколения (#1265); после движения ветки или из другого статуса — новое поколение | `hub/services/lifecycle.py:2400-2435`; до #1265 — 8 дублей (раздел 4) |
| `hub_propose_task` | **второй черновик**: ключа нет | сигнатура в `hub/mcp_server.py:2827` |
| `hub_create_task` | безопасно, если передан `client_request_id` | `hub/mcp_server.py:376-386` |
| `hub_session_register`, `hub_upsert_acceptance_criterion` | идемпотентны по контракту | `hub/mcp_server.py:387-405` |
| чтения (`hub_task_status` и др.) | безопасны | — |

## 6. Варианты лечения и их цена

| вариант | что убирает | цена | риск |
|---|---|---|---|
| **A. Stateless-транспорт** (`stateless_http=True`) | 404 и весь путь восстановления в клиенте: ложной ошибки нет, соблазна повторять нет | S: одна настройка + тесты идентичности + живая проверка клиентов | contextvar'ы bearer/identity могут не дойти до инструмента: задача менеджера создаётся в lifespan. Клиент без `Mcp-Session-Id` не проверен. Хаб не использует серверных уведомлений, сэмплинга и элиситации (греп `ctx.`, `report_progress`, `elicit` пуст), так что функций не теряет |
| B. Сессии вне памяти | 404 после рестарта | L: SDK не даёт подключить хранилище, сессия — это живая задача. Нужен свой менеджер, который «воскрешает» неизвестный id без `initialize` | ломает контракт протокола. `event_store` в SDK даёт только повтор событий потока, а не сессию |
| C. Мягкий рестарт без обрыва (два процесса, передача сокета) | обрыв на время релиза | L: сессии всё равно в памяти старого процесса, новый их не знает. Помогает, только если старый дослуживает клиентов, а это для долгих сессий бессмысленно | сложный деплой ради того, что A делает одной строкой |
| D. Ключ идемпотентности на пишущих вызовах (#1059) | вред от ручного повтора, в том числе при настоящих обрывах сети | M: задача готова, DoR пройден | ложную ошибку не убирает. Защищает только вызовы, которые передают ключ |
| E. Клиент: сообщить о гонке в Claude Code; агентам — «после ошибки сначала статус» | гонку у источника / дубли дисциплиной | вне репозитория / уже в памяти агентов | не в наших руках; дисциплина не является свойством системы |

## 7. Рекомендация

1. **A — заведено #1364** (S, DoR пройден). Ошибка возникает, только если сервер
   отвечает 404 на устаревшую сессию. Без сессий такого ответа нет. Хаб
   сессиями ни для чего не пользуется.
2. **D — #1059 и правило «сначала `hub_task_status`, потом повтор» остаются
   и после stateless.** Stateless убирает 404 после рестарта, но не
   неоднозначный отказ как класс. Обрыв посреди долгой записи (рестарт во
   время выполнения, сеть) снова даст ошибку, по которой нельзя понять, прошла
   ли запись. Раздел 4а показывает, что встречаются оба исхода. Посылка #1059
   «чинить транспорт не надо» уточняется: транспорт чинить **можно**, и это
   убирает основной поток ложных ошибок. Для остатка нужны ключ и чтение
   состояния перед повтором.
3. **E — сообщить о гонке в Claude Code** (гонка фонового переподключения и
   `Retrying tool … after session recovery`). Приложить последовательность из
   раздела 3.

## 8. Что проверить следующим шагом

- #1364 AC-2: в stateless-режиме `principal_id` вызывающего попадает в
  `mcp_call_events`, а инструмент ходит в REST с тем же bearer. Проверять на
  настоящем приложении с токеном, не через `.fn`.
- #1364 AC-3: живой Claude Code на локальном хабе переживает рестарт. В логе
  клиента нет `Session not found` и `Retrying tool`, запись одна. То же для
  Cursor и Codex.
- После выката: в `mcp-logs-<имя сервера хаба>` за неделю ноль строк
  `Session not found`. Это метрика исхода #1364.
- Не наблюдено и стоит отдельного опыта: что получает клиент, если рестарт
  приходится **на выполнение** долгой записи (uvicorn по SIGTERM, закрытие
  lifespan менеджера), и повторяет ли тогда Claude Code вызов сам. Если
  повторяет, это дубль без участия агента, и тогда #1059 срочнее.
