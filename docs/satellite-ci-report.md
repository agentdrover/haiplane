# CI-отчёт из сателлитного репозитория

Хаб не гоняет тесты: решением от 31.07.2026 исполнение живёт в одноразовом
раннере, а хаб принимает и хранит факт прогона. Приёмник репозиторно-нейтрален
(`POST /api/tasks/{id}/ci-run-report`), но производитель доказательств до #761
существовал только в репозитории самого хаба. Этот документ — про то, как
подключить к нему сателлитный репозиторий (Spike_bo, calc-kids и далее).

> **С #1687 хаб принимает отчёт как доказательство, только подтвердив его у
> GitHub, а с #1848 — по контракту CI проекта.** Прямая отправка ключом записи
> из job-а, который гоняет код ветки (раздел «Шаг в workflow» ниже, режим
> `hub-token`), остаётся принятым, но НЕ подтверждается: отчёт такого вида —
> `unverified`, он не открывает ни автовердикт, ни стюарда, ни `ci_before_submit`.
> Подтверждаемый путь — «producer → артефакт → доверенный отправитель → проверка
> хабом», он описан сразу ниже.

## Подтверждаемый путь для спутника (#1848)

Три свойства отчёта хаб различает и проверяет раздельно: **verified**
(происхождение: прогон НУЖНОГО workflow этого репозитория и коммита, текущая
попытка, артефакт `hub-ci-results-<попытка>`, тело совпало), **green** (прогон
закончился `success`, а каждая обязательная проверка контракта — `pass`) и
свои гейты validation и тестовых AC. Меняется только то, какой workflow и какие
проверки считаются обязательными: предикаты те же, что у хаба.

### Контракт CI проекта

Ключ политики проекта `ci_contract` — `{"workflow_path": ".github/workflows/tests.yml",
"required_checks": ["tests"]}`.

- `workflow_path` — файл прямо в `.github/workflows/` (`*.yml` или `*.yaml`);
- `required_checks` — непустой список без повторов из `lint`, `format`, `types`,
  `tests`; хранится отсортированным. Других имён нет и не будет без решения
  владельца: контракт только выбирает из словаря хаба;
- лишние поля — отказ. Без ключа действует контракт хаба (`ci.yml` и все четыре
  проверки), поведение до #1848 не меняется;
- менять может только человек (`PATCH /api/projects/{id}`), в журнале правок
  остаётся «было → стало». Токен агента и ключ `ci_runner` получают 403;
  отложенная правка (`policy-schedule`) с ключом, в том числе с `null`,
  отказывает и при создании, и при исполнении; проект `default` (сам хаб)
  ключ не принимает вовсе.

**Отпечаток контракта** — sha256 канонического JSON
`{"workflow_path", "required_checks"}` (отсортированный список, ключи по
алфавиту, без пробелов); для хаба это отпечаток `{ci.yml, [format, lint, tests,
types]}`. Он записан в каждой попытке и в проекции отчёта. Вердикт проверки
действует только пока отпечаток попытки равен текущему отпечатку проекта: при
смене контракта прежний `verified` и прежний окончательный отказ
(`wrong_workflow`) становятся «требует повторной проверки» (в проекции —
`unverified(contract_changed)`), CI-результаты AC и validation этой попытки не
засчитываются гейтами до нового `verified`, а фоновая проверка берёт попытку
сама, без нового отчёта. Результат проверки, начатой под прежним контрактом,
не записывается.

### Настройка владельцем

1. Принципал `ci_runner` под проект (ключ записи отчёта) и принципал
   `ci_reader`, привязанный к проекту (ключ чтения карточки): `hub-read-token`.
2. В GitHub репозитория спутника — environment `hub-report` с ограничением
   **deployment branches = только default branch** (это настройка GitHub, из YAML
   она не проверяется). В нём — секреты `HAIPLANE_HUB_URL` и
   `HAIPLANE_HUB_CI_TOKEN` (ключ записи). Ключ записи НЕ кладут в секреты
   репозитория и тем более в доступные producer-у.
3. Секреты репозитория для producer: `HAIPLANE_HUB_URL`,
   `HAIPLANE_HUB_CI_READ_TOKEN` (ключ чтения). Прежний секрет с ключом записи,
   которым отчитывался job с тестами, убрать.
4. Два workflow из шаблонов хаба (`hub/workflow_templates/`, формируются
   `hub.services.satellite_ci.render_producer` и `render_sender`):
   `satellite-ci-producer.yml` — job с тестами (без environment и без ключа
   записи: собирает результаты в `hub-ci-results/` и загружает артефакт
   `hub-ci-results-${{ github.run_attempt }}`) и `satellite-ci-report.yml` —
   отправитель, который лежит в default branch, запускается по `workflow_run`,
   привязан к environment и вызывает действие
   `.github/actions/hub-ci-send` хаба с входом `workflow-path`. Отправитель
   читает артефакт как данные, а все факты прогона берёт из события, не из
   артефакта. Проверка имён проверок в отчёте — на стороне хаба: имена вне
   словаря не принимаются, пропущенная обязательная проверка делает отчёт
   подтверждённым, но не зелёным.
5. Записать контракт человеческим PATCH:
   `curl -X PATCH $HUB/api/projects/<id> -H "Authorization: Bearer <токен человека>"
   -H 'Content-Type: application/json' -d '{"gate_policy": {"ci_contract":
   {"workflow_path": ".github/workflows/tests.yml", "required_checks": ["tests"]}}}'`.
   Имена проверок в `checks:` producer-а должны ВКЛЮЧАТЬ все `required_checks`
   (обязательное подмножество, а не «ровно»): лишняя проверка из словаря отчёт
   не ломает, пропущенная обязательная делает его подтверждённым, но не зелёным.
   Отпечаток контракта для сверки лежит в
   `GET /api/projects/<slug>/effective-policy` по пути `keys[].value.fingerprint`
   (элемент `keys` с `key == "ci_contract"`).

`workflow-path` отправителя и `workflow_path` контракта — одно и то же
значение. Если они разошлись, отчёт останется `unverified(wrong_workflow)`:
хаб проверяет по контракту, отправитель лишь не шлёт чужие прогоны.

### Откат

Точный откат к контракту хаба — удаление ключа человеческим PATCH, остальные
ключи политики он не трогает:

```
curl -X PATCH $HUB/api/projects/<id> -H "Authorization: Bearer <токен человека>" \
  -H 'Content-Type: application/json' -d '{"gate_policy": {"ci_contract": null}}'
```

После отката прежние отчёты спутника — `unverified(contract_changed)`, а их
повторная проверка по контракту хаба даст `wrong_workflow`. Отключить сам
отправитель — убрать workflow из default branch или секреты из environment.

### Что хаб не делает

- не ослабляет контракт хаба и не принимает имена проверок вне словаря;
- не подменяет отсутствующую проверку: `missing` и `skipped` обязательной
  проверки — подтверждённый, но не зелёный отчёт;
- не меняет предикаты: любая явная `fail` (в том числе необязательной проверки)
  по-прежнему отвергается гейтом `ci_before_submit`, красная подтверждённая
  проверка по-прежнему удерживает платное ревью;
- не поддерживает проверку на GitVerse: там хаб не видит прогонов CI,
  отчёт остаётся `unverified(forge_unavailable)`.

### Форма validation_commands

Коллектор `hub-ci-report` исполняет строку `validation_commands`, если первый
токен — исполняемый файл. Допустим ведущий префикс окружения
`NAME=VALUE command …` в одну строку. Ограничения на VALUE: простое слово
(до пробела или табуляции) либо `'…'`/`"…"`; в нём нет обратного слэша, а вне
кавычек нет `; & | < > ( )` и обратной кавычки. REST не пуст, и его первый
токен — исполняемый файл (не `;`, `&`, `|`); дальше в REST действует обычный
shell-синтаксис, как и раньше. Перевод строки не допускается. Результат прошлого
прогона для такой строки переиспользуется только при точном совпадении строки.
Правка доходит до спутника после обновления закрепления action `hub-ci-report`.

### Формат доказательства приёмки (для задачи спутника)

Приёмка перевода CI спутника записывается в карточку задачи спутника одним
блоком, на новом SHA ветки задачи (не на прогонах, воспроизводивших
несовместимость):

| Поле | Значение |
|---|---|
| repo | `owner/name` спутника |
| задача / поколение | номер задачи хаба и поколение сдачи |
| SHA | закреплённый коммит |
| ревизии | коммит producer-workflow и коммит sender-workflow в default branch, ревизия `hub-ci-send` |
| прогон | run id, attempt, artifact id, digest артефакта |
| отпечаток контракта | sha256 из `GET /api/projects/<slug>/effective-policy`, путь `keys[].value.fingerprint` (элемент с `key == "ci_contract"`) |
| trust | `verified`, `applied=true`, conclusion=success, checks по контракту = pass, validation=pass, результаты тестовых AC |
| проверенный гейт | `ci_trust.pass_gap` для этих задачи и SHA (по поколению и отпечатку) вернул `None`, либо сдача принята при `ci_before_submit=require` (режим записан) |
| ожидает | шаги владельца, которые ещё не выполнены |

Приёмка через `ci_before_submit=off` не засчитывается.

## Зачем это нужно

Два SDD-гейта (#508/#510) и автовердикт (#745) читают ЗАПИСАННЫЙ результат
прогона по конкретному коммиту. Фраза «прогнал тесты, 94 passed» в тексте сдачи
для них не существует. Пока отчёта нет, бриф честно отвечает «CI не присылал
отчёт о прогоне для коммита …», и вердикт остаётся человеку.

## Что нужно от владельца

1. Отдельный принципал роли `ci_runner` под этот репозиторий — у него ровно
   одно право `tasks.ci_report`. Он не может двигать задачу и не может писать
   вердикт; это не токен исполнителей и не человеческий токен.
2. Два секрета в GitHub сателлитного репозитория:
   `HAIPLANE_HUB_URL` и `HAIPLANE_HUB_CI_TOKEN`.

## Если workflow ещё нет

**Штатное подключение (новый GitHub-проект, #2027).** Провижининг сам кладёт
подтверждаемую пару в репозиторий, где нет ни одного файла в `.github/workflows`
(ни в интеграционной, ни в default-ветке):

- в интеграционную ветку (например `develop`) — `haiplane-ci.yml` (producer,
  `name: Haiplane CI`, шаг отчётности и загрузка артефакта; шаг тестов с
  `id: tests` добавляет владелец, хаб его не угадывает) и `haiplane-stale.yml`;
- в default-ветку GitHub (например `main`, даже если интеграционная другая) —
  `haiplane-ci-report.yml` (sender): `workflow_run` читается GitHub только из
  default-ветки.

Посеянная пара **не считается готовым CI**: `provision_detail` называет оба файла
и статус «ожидает настройки владельцем» с чек-листом — раздел «Настройка
владельцем» выше (`ci_reader` со scope project; `ci_runner` только в environment
`hub-report` с деплоем из default-ветки; старый секрет записи убрать из
репозитория; `ci_contract` `{haiplane-ci.yml, [tests]}` человеческим PATCH).
Пока этого нет, отчёты проекта `unverified`, и `effective-policy` (поле
`ci_trust`) и карточка проекта говорят об этом предупреждением; если отчётов
нет вовсе, фраза другая и это не неисправность. Существующие проекты не
мигрируются: их переводит владелец по этой инструкции. GitVerse не меняется.

**Прежняя прямая отправка (режим `hub-token`).** До #2027 провижининг клал один
`haiplane-ci.yml`, который сам отправляет отчёт ключом записи. Такой отчёт
принимается, но не подтверждается (`unverified(no_provenance)`), и стюард на нём
не ждёт подтверждения: состояние окончательное. На GitVerse и в проектах,
заведённых до #2027, остаётся этот режим: добавить сборку и прогон тестов
этого репозитория (шаблон намеренно не угадывает их) и объявить проекту
`ci_runner` в `gate_policy`, если тесты запускаются не через `uv run pytest`.

Репозиторий, у которого свой CI уже есть, хаб не трогает: там шаг ниже
вставляют руками.

## Шаг в workflow

PR не нужен: отчёт ключуется по КОММИТУ, поэтому push ветки `task-<id>/…`
достаточно — это как раз случай пар-задач, где PR не заводится вовсе.

```yaml
on:
  push:
    branches: ["task-*/**"]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # ... сборка и прогон тестов этого репозитория ...

      - name: Report AC tests and validation to Hub
        if: ${{ always() }}
        continue-on-error: true
        uses: agentdrover/haiplane/.github/actions/hub-ci-report@main
        with:
          hub-url: ${{ secrets.HAIPLANE_HUB_URL || secrets.HAIPLANE_HUB_URL }}
          hub-token: ${{ secrets.HAIPLANE_HUB_CI_TOKEN || secrets.HAIPLANE_HUB_CI_TOKEN }}
          head-sha: ${{ github.event.pull_request.head.sha || github.sha }}
          ac-runner: pytest
```

Три вещи в этом шаге неслучайны.

**`head-sha` передаётся явно.** На событии `pull_request` GitHub кладёт в
`GITHUB_SHA` выброшенный merge-коммит головы в базу. Его нет ни в одной ветке,
и он никогда не совпадёт с вершиной, которую хаб закрепил на сдаче (#572), —
отчёт лёг бы доказательством к коммиту, которого никто не найдёт.

**`ac-runner` — то, чем запускаются тесты ИМЕННО ЭТОГО репозитория.** По
умолчанию `uv run pytest` (способ хаба). Если раннера нет на PATH, каждый AC
отчитывается как `not_found` с причиной — никогда как провал: обвинить работу
в том, что сделал тулинг, хуже, чем промолчать.

**`continue-on-error: true` и `always()`.** Гейт доставки (#605/#606) читает
исход джобы, поэтому шаг отчётности не имеет права ронять её: иначе икота
репортёра заблокировала бы мерж всем задачам сразу.

**Подключаться версией, а не копией.** Копия скрипта в сателлите разъедется с
оригиналом молча; `@main` (или закреплённый тег) — нет.

## Что читает хаб, если отчёта не пришло

Молчание — это `unknown` с названной причиной, никогда не успех и никогда не
провал. Отсутствие секретов (форк, чужой PR), отсутствие раннера, недоступный
хаб — всё это печатает причину в лог шага и завершается кодом 0.

## Чего этот шаг НЕ делает

Он не решает, прошла ли задача: он приносит факты. Отчёт засчитывается только
для коммита, закреплённого хабом на сдаче; отчёт про другой коммит хранится как
доказательство про тот коммит и НЕ применяется — так гейт нельзя открыть кодом,
который никто не гонял.
