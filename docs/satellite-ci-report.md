# CI-отчёт из сателлитного репозитория

Хаб не гоняет тесты: решением от 31.07.2026 исполнение живёт в одноразовом
раннере, а хаб принимает и хранит факт прогона. Приёмник репозиторно-нейтрален
(`POST /api/tasks/{id}/ci-run-report`), но производитель доказательств до #761
существовал только в репозитории самого хаба. Этот документ — про то, как
подключить к нему сателлитный репозиторий (Spike_bo, calc-kids и далее).

## Зачем это нужно

Два SDD-гейта (#508/#510) и автовердикт (#745) читают ЗАПИСАННЫЙ результат
прогона по конкретному коммиту. Фраза «прогнал тесты, 94 passed» в тексте сдачи
для них не существует. Пока отчёта нет, бриф честно отвечает «CI не присылал
отчёт о прогоне для коммита …», и вердикт остаётся человеку.

## Что нужно от владельца

1. Отдельный принципал роли `ci_runner` под этот репозиторий — у него ровно
   одно право `tasks.ci_report`. Он не может двигать задачу и не может писать
   вердикт; это не токен исполнителей и не человеческий токен.
2. Два секрета в GitHub сателлитного репозитория:
   `OPENCLAW_HUB_URL` и `OPENCLAW_HUB_CI_TOKEN`.

## Если workflow ещё нет

С #476 его кладёт провижининг: в репозиторий, где нет ни одного файла в
`.github/workflows`, хаб коммитит `openclaw-ci.yml` (и `openclaw-stale.yml`) с
уже подставленными ветками проекта и уже вписанным шагом отчётности ниже.
Остаётся добавить туда сборку и прогон тестов этого репозитория — шаблон
намеренно не угадывает их — и объявить проекту `ci_runner` в `gate_policy`,
если тесты запускаются не через `uv run pytest`.

Репозиторий, у которого свой CI уже есть, хаб не трогает: там шаг ниже
вставляют руками.

## Шаг в workflow

PR не нужен: отчёт ключуется по КОММИТУ, поэтому push ветки `task-<id>/…`
достаточно — это как раз случай пар-задач, где PR не заводится вовсе.

```yaml
on:
  push:
    branches: ["task-*/**"]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # ... сборка и прогон тестов этого репозитория ...

      - name: Report AC tests and validation to Hub
        if: ${{ always() }}
        continue-on-error: true
        uses: mrPDA/openclaw-hub-standalone/.github/actions/hub-ci-report@main
        with:
          hub-url: ${{ secrets.OPENCLAW_HUB_URL }}
          hub-token: ${{ secrets.OPENCLAW_HUB_CI_TOKEN }}
          head-sha: ${{ github.event.pull_request.head.sha || github.sha }}
          ac-runner: pytest
```

Три вещи в этом шаге неслучайны.

**`head-sha` передаётся явно.** На событии `pull_request` GitHub кладёт в
`GITHUB_SHA` выброшенный merge-коммит головы в базу. Его нет ни в одной ветке,
и он никогда не совпадёт с вершиной, которую хаб закрепил на сдаче (#572), —
отчёт лёг бы доказательством к коммиту, которого никто не найдёт.

**`ac-runner` — то, чем запускаются тесты ИМЕННО ЭТОГО репозитория.** По
умолчанию `uv run pytest` (способ хаба). Если раннера нет на PATH, каждый AC
отчитывается как `not_found` с причиной — никогда как провал: обвинить работу
в том, что сделал тулинг, хуже, чем промолчать.

**`continue-on-error: true` и `always()`.** Гейт доставки (#605/#606) читает
исход джобы, поэтому шаг отчётности не имеет права ронять её: иначе икота
репортёра заблокировала бы мерж всем задачам сразу.

**Подключаться версией, а не копией.** Копия скрипта в сателлите разъедется с
оригиналом молча; `@main` (или закреплённый тег) — нет.

## Что читает хаб, если отчёта не пришло

Молчание — это `unknown` с названной причиной, никогда не успех и никогда не
провал. Отсутствие секретов (форк, чужой PR), отсутствие раннера, недоступный
хаб — всё это печатает причину в лог шага и завершается кодом 0.

## Чего этот шаг НЕ делает

Он не решает, прошла ли задача: он приносит факты. Отчёт засчитывается только
для коммита, закреплённого хабом на сдаче; отчёт про другой коммит хранится как
доказательство про тот коммит и НЕ применяется — так гейт нельзя открыть кодом,
который никто не гонял.
