# Invariants

These are the rules most likely to be broken by “small” changes.

## Domain Invariants

- Task hierarchy is strict: `epic -> feature -> task -> subtask`.
- Agent-created work starts as `draft` — including `epic`/`feature` proposals (#323); human-created work usually starts as `open` unless run immediately.
- Human-created `epic` and `feature` items are created as `open`; epics and features never auto-run and never auto-review.
- `subtask` items must not auto-enable review by default.

## Lifecycle Invariants

- Status values are defined in `hub/models.py:TaskStatus`.
- Final statuses are `completed`, `failed`, `rejected`.
- Active statuses are tracked by `ACTIVE_STATUSES` in `hub/models.py`; progress math depends on them.
- A `done` report from a disallowed status must not create a duplicate done row;
  the API returns HTTP 400/409 with `{reason, hint, required_status}`.
- On pair `running` (no `job_id`) or `claimed`, a valid done report routes through
  the shared post-done transition (blocker → `needs_decision`, else the
  Universal Review Gate below); completing `claimed` clears the claim.
- Universal Review Gate (#306): normal completion paths (done reports on
  pair/claimed/pending_report) complete a task only when
  `completion_requires_review` is false — i.e. `auto_review` is off (explicit
  opt-out) or the CURRENT submission generation has an APPROVED verdict.
  Otherwise the done report is a submission: → `ci_check` when a `branch`
  exists (conveyor), → `review` (client-driven, no `review_job_id`) without
  one, → `needs_decision` at the review-cycle limit. Completing approved work
  must NOT bump the submission generation (it would invalidate the approval).
- Review is submission-bound: `hub_submit_for_review` (or a routed done report)
  bumps the submission generation, which makes prior verdicts and reports stale.
  Exception (#1265): a resubmit from `review` on the SAME non-empty sha keeps the
  generation, the status and the verdict's currency (`finding_outcomes`,
  `accept_areas` and the decision to order a review may still update).
- Submit with `expected_sha` (#1937): optional, exactly 40 ASCII hex (case folded; short or non-hex = 422 on REST, a local error in `oc-hub submit-review --expected-sha` and in `hub_submit_for_review` before any network call; state tasks = 422). The value is a CLAIM, never pinned: `expected_sha_gate.refuse_unless_head_is_expected` (the verdict itself is `head_refusal`, computed without a write; a dry run, #1975, raises it and writes no alert) runs inside `pin_submission_sha` right after the hub's own `resolve_branch_tip` and BEFORE `ci_trust.refresh_quietly`/`invalidate` and the same-sha no-op (#1265). Observed head != claim = 409 `head_moved` (`expected_sha`, `observed_sha`); no observation or a non-sha one = 409 `head_unverified` (`cause`) — "could not look" is not "matches". The only write on refusal is one `alert` with both shas; no PR, dispatch, generation, outcomes, prevention or areas. `submission_sha` is the single observed tip (no second resolve). Refusal exists on the pair chain only; `HEADLESS_STEPS` pass an empty body. Known window: observation happens before the write transaction, as before.
  Fixes after `changes_requested` reach review only via a resubmit of the SAME
  task on the SAME branch — pushing commits alone does not re-trigger review.
  A review of task A never sees task B's branch; do not base new task branches
  on unmerged branches under review (see `docs/repository-rules.md`,
  «Жизненный цикл ветки задачи»). The stacking *advisory* (#438) judges
  pushed refs (`_resolve_ref_remote_first`): a stale local `develop` in the
  hub clone must not invent a stack or tell the implementer to merge another
  task's unreviewed branch (#1046).
- Finding routing (#435, #437): `in_scope` findings are closed ONLY via a
  resubmit of the same task on the same branch (`changes_requested` →
  `running` → fix → `hub_submit_for_review`). Never spawn parallel tasks for
  in-scope findings (incident #392). `out_of_scope` findings go to separate
  tasks referenced by `linked_task_id` and never block the verdict.
- Delivery PR for confirmed commits (#967): a pair task whose branch
  verifiably carries commits (`branch_diff_paths` → non-empty list) does not
  submit or complete without a PR — the hub pushes the branch and opens one
  itself (`ensure_delivery_pr`), at submission and at done. If commits are
  confirmed and the PR cannot be opened, the done report goes to
  `needs_decision`, not `completed`. The block arms ONLY on positive
  knowledge: `None` ("could not look") and `[]` (empty diff) keep the old
  path — the #498/#767 line that ignorance is not an accusation. Boundary:
  the invariant sees only what the hub's clone and origin see; a branch that
  exists solely in a foreign unpushed clone stays silent (#966's territory).
  This deliberately RETIRES the old carve-out "a task with a branch and no
  PR completes as before" for anything with observable commits.
- Delivery-gate refusals split three ways, by WHO has to act (#951, #1030, #1041, #1053).
  Transient (`ci_pending`, `ci_unavailable`, `ci_missing_run` within the CI
  grace window, `pr_draft`): nobody acts, the task stays `running` and the hub asks again.
  After the window a missing run becomes terminal `ci_untested` naming the
  commit. A GitHub draft after Hub APPROVED is transient, not recoverable: the
  hub marks the PR ready (approval is the ready signal) and retries;
  resubmitting would stale the verdict (#612) with no new commits. Recoverable
  (`ci_failed`, `stale_approval`): the EXECUTOR acts, the task stays `running`,
  and the hint names `hub_submit_for_review` — a fix is new commits, so
  delivery needs a new review (#612), never another done report. Terminal
  (`merge_failed`, closed PR, `no_pr`, `merge_gate_error`, `ci_untested` past
  the window): a human acts, `needs_decision` as before.
  Waiting on a recoverable refusal is bounded twice, because two different
  things can go wrong: the fix budget (`ci_fix_cycle` vs `MAX_CI_FIX_CYCLES`,
  charged once per submission — the same budget the headless conveyor spends)
  stops an executor that keeps failing, and session presence stops a task
  nobody works on any more. `running:pair` has no machine deadline, so the
  #418 backstop does NOT cover this — the bounds above are the only ones.
- Human overrides bypass the gate by design and stay audited: `POST /api/tasks/{id}/decide`
  accept and `force_complete`.
- Parent rollup: completing the last child `task` under a `feature` (or the last
  `feature` under an `epic`) auto-completes the parent when all siblings are
  `completed` (idempotent).
- `force_complete` is the audited human override for `task`/`subtask` rows:
  allowed from any non-terminal status when no *active* dispatch job backs
  `job_id` or `review_job_id` (409 if active; missing/terminal jobs are
  audited and allowed). A non-empty comment is required for active lifecycle
  states other than `pending_report`/`claimed` (those two may fall back to
  the default audit message). Clears stale claim metadata. Rejects terminal
  tasks and `epic`/`feature` rows with incomplete descendants.
- Write serialization (`get_write_lock`) covers refinement/AC paths,
  `create_subtasks_bulk`, and the lifecycle completion paths (`add_update`
  done-flow, `force_complete_task`). It is NOT yet a full per-connection
  commit lock; broad commit serialization is tracked as hardening work.
- No write lock across the network (#2001): a write made BEFORE a forge/git call on the delivery path (`deliver_on_disposition` alert, `_live_pr_for_branch` / `pr_for_delivery` / `ensure_delivery_pr` PR number, the `_approved_code_check` re-pin) is committed before the call by the owner of its transaction (`hub.db.committed_if_own`: a write on a clean connection is committed by its author; a transaction opened before the write is foreign, is neither committed nor rolled back by the block, and `delivery_rerun._reserve_and_post` still refuses a paid POST inside it). Guard: `tests/test_no_lock_across_network.py`. Since #2005 the same rule holds for `poller._sweep_ci_check`: the pass owns its connection, and its own writes (the CI-state reset, the `absent` note) are committed before `dispatch_review` / `get_ci_failure_logs`. EXPLICIT EXCEPTION (#2005): BOTH entries of `orchestration._route_after_done` KEEP the write lock across the git tail (`content_differs`, `push_branch`, `create_pr`). The done-flow entry (`task_updates.apply_update`: `write_transaction` + `SAVEPOINT done_flow`) is a foreign transaction: a commit would release the savepoint and void the #364 rollback. The headless entry (`poller._sweep_running_dispatch` -> `transition_after_agent_done`, `lifecycle.refresh_task`) is foreign too: `critic_orders.accept_in_transaction` leaves the `submission_generation` bump uncommitted on purpose, and the boundary is the commit right after `transition_after_agent_done` returns (`poller.py` in `_sweep_running_dispatch`). If the tail raises, `poller._task_isolation` rolls back what the task left uncommitted BEFORE it swallows the exception, so the next sweep's commit (`_sweep_events_retention` commits unconditionally) cannot persist a bump with `status=running`; the tick-end rollback in `_poll_once` does not cover this (no open transaction is left by then). The bump and the route commit atomically; releasing the lock needs the network moved out of the tick (separate work). Guards: `test_done_flow_entry_never_commits_the_foreign_transaction`, `test_headless_route_never_commits_the_generation_bump_before_the_network`, `test_failed_tail_in_a_real_tick_does_not_persist_the_generation_bump`. Known, not fixed: headless `poller._record_merge_and_tidy`.
- Approval is only valid from `draft`.
- Approval uses an atomic conditional transition to avoid double-processing races.
- If required DoR checks fail and `force` is not set, approval must fail with HTTP 422.
- If concurrent approval loses the race, the caller should see HTTP 409, not silent success.

### Verdict of a commit task is not replaced silently (#1706)

- ONE writer: `hub/repository_verdict.write_review_verdict` (behind `repository.record_review_verdict`). Every condition is in the UPDATE: the live generation equals the named one; no verdict stands on it, or `review_verdict_revision` equals `supersedes_revision` and the #1286 window is not closed. `review_verdict_revision` grows on every write by every writer (REST, web, steward, autopilot, poller).
- Before the write, `hub/services/verdict_guard.decide` gives the readable answer: first write / repeat (same kind + findings + comments, by `tasks.review_verdict_digest`: 200, no write, no feed line, no follow-up drafts) / 409 naming kind, revision, time, author and `supersedes_revision=R` / replacement. Replacement needs an authenticated human, `expected_generation` and the current revision; the feed says "вердикт заменён: было X (ревизия R), стало Y". Automation (steward, autopilot) has only the first write; a closed window answers 409 "нужна новая сдача".
- The studied generation: `expected_generation` is in the body (REST, CLI `--expected-generation`, MCP `hub_submit_review`, web hidden field) and comes from the review brief; the CLI never fills it in. A write without it is accepted but answered with a warning.
- The poller does not rewrite a stored verdict; a scanned CHANGES_REQUESTED is written only for the generation the tick read and only where no verdict stands, and its result is checked.
- Known boundary: follow-up drafts are created before the write transaction (`create_task` commits on its own), so two concurrent identical first writes may leave one idempotent (marker-reused) draft; the verdict itself is atomic.

## Structured Form Invariants

- Structured fields are stored on the `tasks` row except acceptance criteria, which live in a separate table.
- Risks are stored as JSON on the task row.
- `TaskRefine` is PATCH semantics: omitted fields must remain unchanged.
- Unknown `work_type` falls back to the strict `feature` DoR profile.

## Surface Alignment Invariants

- REST API is the canonical behavior surface.
- MCP tools should mirror API behavior; they should not introduce separate business rules.
- CLI should stay behaviorally aligned with API contracts and error handling.
- If request or response models change, affected API, CLI, MCP, and tests should be reviewed in the same pass.

## Persistence Invariants

- Schema changes belong in `hub/migrations/` (the list), applied by `hub/db.py`. Migrations are one file each (#1854): `hub/migrations/steps/m<YYYYMMDDHHMM>_<task>_<what>.py`, found by the loader and appended after the FROZEN `part_1..3` in file-name order. A merged step file is never edited or deleted (`scripts/migration_steps_add_only.py`, in `make check` and CI; on push the base is `github.event.before`, in a PR the PR base); a fix is a new file with a new name. A step is data: a docstring and one literal `MIGRATIONS = [...]`, read with `ast.literal_eval` and never executed (a call, an import or `"a" + "b"` is rejected). Startup skips stray files in `steps/` with a log warning; CI fails on them. Independent steps must tolerate any delivery order (a later-named step may be applied before an earlier-named one arrives); a dependent step goes in a later-named file and the tasks carry a dependency. The runner applies each tuple as a separate statement: a file is not atomic as a whole.
- Repository helpers must serialize and deserialize structured list/JSON fields consistently.
- It is safer to fail loudly on missing structured columns than silently treat them as empty.

## Integration Invariants

- Core code depends on plugin protocols, not concrete integrations.
- No-op plugins are valid runtime behavior and should keep the app usable without external binaries.
- Dispatch, git, GitHub, transcripts, and Vast integrations are optional adapters, not prerequisites for core task CRUD.
- Review not bought on red CI (#1405): the decision is made ONCE, in `_policy_and_novelty_allow` right after the policy check and before the ladder/cascade/ask-again bypass, from the CI report for the PINNED sha present at that moment. A report naming `fail` (checks or `validation_status`) buys no run and writes one `review_withheld_red_ci` event per generation with the failed checks and the way out (resubmit or `machine_review_override=require`); a red report refuses every entry, including a ladder/cascade/ask-again top-up after a run was already bought (then one `review_topup_withheld_red_ci` event instead); `unknown`/`skipped` are not red. No report: the order goes as before, plus one `review_ordered_without_ci` line per generation. There is NO deferred order: neither `accept_ci_run_report` nor the poller orders a review. Events are deduplicated by `events` kind + `payload.generation`, never by feed text.
- Review circle stops deep (#1432): an unnamed finding outcome is unknown and does NOT break the circle chain; only a clean complete report or an explicit refusal (`false_positive`/`not_a_defect`/`wont_fix`) of ALL findings of a generation does. At `circle_deep_stop` laps (gate_policy key, else `REVIEW_CIRCLE_DEEP_STOP`, default 2; 0 or unreadable = off) a submission the rule gives deep gets lite with the reason `круг: N заходов, deep приостановлен до решения человека` plus the cancelled deep reasons, and the ladder (#879) / second axis (#1243) forced deep is refused in `_policy_and_novelty_allow` with a named reason. `machine_review_override=require` and a declared security risk keep deep. One `review_circle_deep_stopped` event + alert per generation, deduplicated by `events` kind + `payload.generation`.
- Review-dispatch billing (#1026): `cursor_cloud.get_usage` is stamped on `review_dispatches.provider_tokens` for every terminal close (`done` and `failed`). NULL is unknown; 0 is a billed zero. Wasted spend of failed runs is a sibling of `machine_reviews` and must not enter `tokens_per_confirmed` / `provider_tokens_per_confirmed` (#516).
- Shared project workspace (`workspace_path`): pair-start may auto-switch away from a **clean, pushed** `task-N/*` branch (#451); dirty or unpushed foreign branches still block with 422. After submit-for-review, report-done, or release, Hub best-effort checks out the project base branch when the workspace is clean and on that task's branch.
- Pair-start `git_mode=remote` (#975) records the canonical `task-<id>/<slug>` name and skips host git at prepare, restore (submit/done/release), and switch (CHANGES_REQUESTED / worktree recreate). Omitted/`hub` keeps today's laptop path. Remote submit-review on a project without `repo`/`gh_repo` names that diff/PR could not be made on the response (lifecycle_hint); it must not look like empty success. Laptop `git_mode=hub` still treats "could not look" as not an accusation (#498). GET `/api/tasks/{id}` and `/context` fill `worktree_path` only when a pair worktree is still registered (`worktree_is_registered`), not by status (#989): `submit_for_review` removes the tree; headless `start_task` never creates one; `git_mode=remote` has no hub-host tree. A session.workspace mismatch is an advisory line on `/context`, never HTTP 409.
- Session registry ownership (#977): `POST /api/sessions/register` must not overwrite another principal's `principal_id` or `agent` (HTTP 409, row unchanged). `POST /api/sessions/{id}/heartbeat` from a foreign principal is HTTP 404 with the same body as an unknown id and must not bump `last_seen_at`. Same-principal re-register stays 200 and refreshes `last_seen_at`.
- Chat-pair implementer (#980): sibling `kind` on the same code machinery, not a flip of intake #961. Intake `role=human` / `CHAT_PAIR_PERMS` / create stay. Implementer is issued only from `open`, acts as `role=agent` with `CHAT_PAIR_IMPLEMENTER_PERMS` (no `tasks.create`), and `{task_id}` outside `bound_task_id` is 403 `chat_pair_gate_forbidden`. Revoke is scoped by kind so intake and implementer do not kill each other. Missing acting principal is 503 on issue and indistinguishable 401 on redeem. The open task card issues that code (#981); `/chat-pair` stays intake copy and counts only intake sessions. Operator path is guide §4b, not §4a. Cloud implementer pair-start uses `git_mode=remote` so host git is skipped (#975) — that skip is the same invariant as the previous bullet, not a second git mode. Implementer session TTL is the same `CHAT_PAIR_TTL_SECONDS` as intake, with ONE exception (#1960): an order to a registered executor host (`channel=slot`) carries `executor_orders.run_seconds`, a snapshot taken at issue from the task size (`hub/services/order_deadline.py`, env `HAIPLANE_EXECUTOR_RUN_SECONDS`, default 7200 for every size, floor 3600, code ceiling 14400); its session lives `run_seconds` from the FIRST redeem and rotation never extends it. Cloud, intake and manual implementer codes keep `CHAT_PAIR_TTL_SECONDS`. There is no renew (#983, allowlist stays closed). When the last live implementer session for that bound task expires or is revoked while the task is still `running` or `claimed` (pair, no `job_id`), the chat-pair reaper returns the task to `open` with a recorded status update before deleting the session row. A dead sibling must not yank a task that still has another unexpired, unrevoked implementer session. Intake expiry does not move tasks. Review/completed are left alone.
- Reviewer code window and refusal reason (#1694): the `reviewer` chat-pair code has its own TTL, `CHAT_PAIR_REVIEWER_CODE_SECONDS` (env `HAIPLANE_CHAT_PAIR_REVIEWER_CODE_SECONDS`, default 3600 s); every other kind keeps `CHAT_PAIR_CODE_SECONDS`. Single use, task/generation binding, burn-on-reissue and the session TTL are unchanged. `purge_expired` keeps reviewer rows `CHAT_PAIR_SPENT_RETENTION_HOURS` (24 h) after `expires_at` (spent ones after `redeemed_at`) so a refusal can be explained; other kinds are dropped as before. A refused redeem is explained ONLY in the closed admin audit (`chat_pair_redeem_refused`, read with `admin.audit.read`): one closed reason per branch (`spent` before `expired`, then `principal_inactive`, `task_not_in_review`, `generation_mismatch`, `implementer_refused`, ..., `unknown`), kind and binding, never the code, its hash or the address; NOT in the event feed (agents read it) and NOT in the response, which stays the one indistinguishable 401 `chat_pair_invalid` (429 and the implementer 409 as before). `unknown` is thinned to one audit row per client address per 60 s by a counter of its own in process memory, separate from the limiter. A failed audit write must not change the answer.
- Steward principal (#1021): role `steward` is neither human nor agent. `is_human` is false even when `tasks.human_gate` is absent and `principal_id` is set; `is_agent` is false so "not an agent" must not be read as "a human". Access is deny-by-default: `STEWARD_ALLOWLIST` is two routes (GET evidence pack, POST judgement). A new route is 403 until it is listed explicitly. `CHAT_PAIR_PERMS` is the pattern, not the permission set.

Since #1924 the judge (`kind='verdict'`) no longer reaches that storage with a bare body: an `approve`/`changes_requested` without a counted ground (a ground counts only with non-empty `detail`) or without `confidence` (other than `low`, which still downgrades) gets 422 `steward_judgement_incomplete` with the missing fields and a body sample, NOTHING is written, and the order stays open so the judge fixes the body in the same run; not fixed by the deadline = the run closes (`run_timeout`) and the decision goes to the human. A ground whose `detail` still contains the service marker `__ЗАПОЛНИ_ФАКТ_7Q__` (`steward_judgement_sample.DETAIL_MARKER`; checked after NFKC, with whitespace/invisible characters removed, casefolded) is not counted for the judge; the rule is by CONTENT, never by the look of the text (`<none>` or `<ci_run=1>` are real facts), and the advisor keeps its #1671 behaviour. The sample itself is not executable as it stands (marker in `detail`, hints in angle brackets for verdict, confidence, source). Each refusal is an event `steward_judgement_refused`, counted as `refused` in the `gate=steward` row next to `escalated`. An answer without grounds and confidence is never stored as applicable and never applied on any path; the storage downgrade stays as a backstop (also for `dor`/`disposition`, where empty details still count). At-most-once on `(task_id, generation, kind)`. Closures address findings by `finding_uid` of that generation's report.

- Rework decision consumes the `needs_decision` entry once (#1991): `decide_task` (REST, MCP, CLI, web form, card sheet all converge there) takes the entry inside ONE `write_transaction` together with the decision record: `rework_launch.reserve` re-reads the task (status must still be `needs_decision`, else 409), refuses while a booking is active or an executor run is live, and inserts a `rework_launches` row in state `reserved`. The partial UNIQUE index `idx_rework_launches_one_reserved` (one `reserved` row per task) is the guarantee, not the process lock of the sheet (#1813). `accept` takes the entry under the same lock (`rework_launch.require_entry`), so it can neither overwrite a rework in flight nor be written twice; `executor_launch._live_run` reports an active booking, so the merge/repair/submit-only runs refuse too. The loser gets 409 and writes nothing. The dispatcher call goes AFTER the booking commit, without a write lock; its outcome is written conditionally in one transaction: `launched` (status `fix_requested` + `job_id`) or `declined` (no job_id: status `open`). The dispatcher has no idempotency key, so a call cut off by a crash or timeout leaves the booking `reserved` (a repeat decision is refused) and the poller sweep `rework_launches` reconciles bookings of a PREVIOUS hub process (`rework_launches.boot_id` != `BOOT_ID`), bookings whose sender has finished (`release_sender` clears `boot_id`) and the last unresolved `needs_human` order of a task: it looks for the booking marker `rework-launch:<id>` (carried in the order text) in the dispatcher's recent jobs; found = the task is linked to that job, not found = state `needs_human`, an alert with the reason, the task stays in `needs_decision`, and NO re-launch happens; the human decides again knowingly.
- Rework recovery rests on process boundaries, not on time (#1991): a booking is never closed by a timer, because time does not prove the sender stopped. Two assumptions carry it. (1) One hub process per database: `rework_launch.claim_process` takes `flock` on `<db>.owner.lock` once per process in the lifespan; a second instance neither sweeps nor orders rework (503) until it gets the lock itself. (2) The service manager kills the WHOLE process group of the hub on stop or crash, so a child `submit` of a dead hub does not outlive it: on prod `systemctl show <hub unit> -p KillMode` = `control-group` (checked by the owner on 24.10.2026). A hub started outside such a manager (a bare shell, `KillMode=process`) is NOT covered: its orphaned child can still create a job after the next boot reconciled the booking. A cancel or failure on any await after the booking commit, the COMMIT itself included, calls `release_sender`, so a finished sender never leaves a `reserved` booking behind.

## Review dispatch: обоснования, вынесенные из комментариев (#2066)

Сжатие истории в `hub/services/review_dispatch.py`; в коде остались инвариант и главная ссылка, здесь — то, что нужно, чтобы не повторить дефект. Имена функций ищите в файле.

- **Вторая дверь (#1252, #1266, #1242).** Отказ облака бывает СИНХРОННЫЙ (агент не создался, денег не потрачено по наблюдению; оплаченного агента, найденного позже, принимает сохранённая заглушка, #1946; `maybe_dispatch_review`) и АСИНХРОННЫЙ (агент создался, прогон кончился без отчёта, прогон уже оплачен; `sweep_review_dispatches`): оба места зовут `open_second_door`, закрыть одно значит оставить половину сдач без отчёта. При СИНХРОННОМ отказе долг записывается строкой-заглушкой ДО попытки открыть дверь (иначе падение внутри `open_second_door` не оставляет свипу ничего повторить); заглушка создаётся и удаляется только на этом пути (`_owe_the_refused_call`). При АСИНХРОННОМ отказе заглушки нет: долг пишется на СУЩЕСТВУЮЩЕЙ строке оплаченного заказа (UPDATE по id), и при локальной замене эта оплаченная облачная строка сохраняется — «ровно одна строка, локальная» к этому пути не относится; строка не закрывается раньше, чем долг отдан (закрытая строка невидима свипу, поллер глотает исключение). Заглушка без агента не считается ступенью лестницы. Синхронный отказ, открытая дверь: заглушку удаляет вызывающий (в итоге ровно одна строка, локальная), КРОМЕ заглушки, на которую указывает код, сессия или отчёт (#1946, `_owe_the_refused_call`: она нужна для приёма позднего облачного отчёта); синхронный отказ, закрытая дверь: заглушка остаётся `failed` — по ней `_ask_again_lost_reviews` переспрашивает облако. Свежесть сдачи и достижимость перечитываются внутри `open_second_door` (между заказом облака и развилкой лежит сеть), отчёт проверяется дважды: рунг-совпадением в `_second_door_after_run` и ПОСЛЕДНИЙ раз в `dispatch_local_review` перед вставкой строки; проверка именно рунг-совпадением, а не «есть ли хоть какой-то отчёт поколения» (у добора лестницы #879 отчёт предыдущей ступени законно есть). Замена не вправе ПОНИЖАТЬ deep упавшего заказа: форсируется только deep, для lite профиль считается заново (он может и повыситься). Один потребитель правила не равен всем потребителям: проверять каждое место применения.
- **Слепой исход (#1199, #1399).** Пустой `agent_id` у заказа с признаком blind значит «спросить, создался ли, не вышло», а не «не создан»; повтор и вторая дверь на нём запрещены, отказом считается только наблюдённый факт (провайдер отверг создание или сверка подтвердила отсутствие агента), слепота остаётся человеку. На слепом пути долг второй двери НЕ пишется, `_release_the_order` не вызывается (функция возвращает False), и бронь держится весь `REVIEW_ORDER_CLAIM_TTL_MINUTES`, чтобы следующий триггер не купил второго ревьюера поверх, возможно, уже оплаченного. Неслепой синхронный отказ: бронь снимается только ПОСЛЕ записи и разбора долга (`_owe_the_refused_call`, затем `_release_the_order`), иначе триггер между алертом и заглушкой купил бы облачного ревьюера, пока вторая дверь открывает локального.
- **Ступени лестницы и пары «заказ — отчёт» (#879, #1025, #1242, #1252).** Лестница даёт два заказа ОДНОГО принципала на поколение; отчёт сопоставляется заказу сначала по явной привязке `dispatch_id` (#1946), а среди непривязанных — по порядку: k-й заказ ждёт k-й отчёт принципала. Ступень считается среди заказов того же принципала И канала (облачный и локальный заказы живут в одном поколении, принципалы разные, #1128). Заказ, замещённый переспросом того же канала, ступени не занимает; замена другим каналом (второй дверью) — занимает, у неё свой порядок.
- **Переспрос (#1242).** Кандидат — последний заказ поколения, облачный и упавший, у сдачи, которая его ещё ждёт. Это не лестница добора (та идёт по существующему неполному отчёту), не обход стража второй читки (повтор идёт через `maybe_dispatch_review` без `force_profile`) и не вторая дверь. Попытка без строки заказа — не всегда слепой исход: отказ конфигурации, политики или стража тоже не оставляет строки, причина уже в карточке алертом.
- **Вторая ось каскада (#1243, #1238).** Профиль не меняет, меняет модель; применяется там, где лестница на deep молчит (по спайку #1168 30 из 51 неполного отчёта за 90 дней уже deep). Она не заменяет переспрос и не лечит отказ среды (другая модель упрётся в то же). Польза не доказана — у оси свой счёт исхода (`count_model_cascade_outcomes`). Проверяется ДО потолка лестницы: lite → deep-добор → deep-неполный — две оплаченные ступени, потолок охраняет третью ступень ПРОФИЛЯ.
- **Круг ревью (#1235, #1432).** Считаются поколения, а не возвраты, и ничего не останавливается из-за счёта: находки в таком круге настоящие (в замере 24 из 25 неразрешённых за день), потолок вытолкнул бы к человеку работу, шедшую верно. Хаб называет круг и зовёт человека. С #1432 остановка deep кругом удерживает и добор, и вторую ось, а пересдача получает lite, КРОМЕ просьбы человека и риска security: они сохраняют deep.
- **Покрытие кода и самоотчёт (#762, #1011, #1025, #1400).** «Код прочитан» = отчёт ПОЛНЫЙ и независимый. Неполный отчёт сам говорит, что дочитал не всё; самоотчёт исполнителя не отменяет независимого ревьюера (автор уже закрывал чужой диспетчер как выполненный). Незнание не есть совпадение: нет закреплённого sha — оснований считать код прочитанным нет, повторное чтение не запрещается (сам заказ без текущего sha диспетчер не запускает). Фильтр по поколению в `_report_already_covers_this_sha` — `<=`, потому что пересдача того же sha из review (#1265) поколение не поднимает.
- **Профиль ревью (#807, #820, #1415, #1416).** Глубокий харнесс покупают класс риска, поверхности процесса и декларированный риск security; декларированный `high` другого рода deep не покупает (замер #1415: 0,54 подтверждённых находки на отчёт против 1,02 у lite, ≈4M токенов против ≈1,7M). Предмет профиля — дифф АВТОРА (#1249): документы, пришедшие со слиянием базы, не прячут код автора и наоборот; неустановленное происхождение читает всё и говорит об этом. Малая пересдача (#1416) и документация идут на lite, кроме просьбы человека, security и исправления прод-регрессии (#1858: `found_in=prod` вместе с `cause_kind=regression` сохраняют deep даже для документации и малой дельты).
- **Токены и бюджет (#893, #1252).** В промпте нет числового потолка токенов: число ничего не ограничивало (счёт провайдера считает контекст, вызовы инструментов и повторные проходы); для lite форму прогона задаёт поведение — один проход по диффу (deep идёт по multi-agent-review с фазами). Потолок стоимости второй двери считает и токены оплаченных прогонов без отчёта (`review_dispatches.provider_tokens`, #1026), `NULL` остаётся незнанием и склоняется в сторону прогона.
- **Доставка отчёта текстом (#1036).** MCP хаба не доезжает до облачного прогона, поэтому блок отчёта в конце текста — второй, более слабый канал; происхождение отчёта пишется в данные, владелец берётся из строки диспетчера, а не из самоназвания отчёта (#1025).
